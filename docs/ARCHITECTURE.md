## 1. Purpose and scope

This document describes the software architecture of DelphosFootball: the system that identifies economically undervalued football players from the "Football Data from Transfermarkt" Kaggle dataset, as scoped in [docs/CONTEXT.md](CONTEXT.md). It exists so that a new engineer can understand the system's components, their contracts, and the reasoning behind the major technology choices without reading the code first.

The audience is an experienced engineer joining the project, plus the two-person course team.

**Out of scope:**

- **ML algorithm design.** The modeling methodology (K-Means clustering, linear and polynomial regression, Random Forest classification; see docs/CONTEXT.md sections 4-6) is deliberately deferred. This document treats the ML pipeline as a black-box "offline pipeline" component. Its internal design — feature engineering, model selection, evaluation strategy — is deferred to [docs/ML_ARCHITECTURE.md](ML_ARCHITECTURE.md).
- **Delivery schedule.** The course schedule, actual progress, and variances live in [docs/WORK_PLAN.md](WORK_PLAN.md). The delivery priority across components is [ADR-007](#adr-007-delivery-priority-under-the-course-deadline).

## 2. System context

DelphosFootball is an internal scouting tool. Its primary users are:

- **Club analysts / directors** — interact with the Flutter app to search players, inspect valuations and undervaluation findings, browse player archetypes, and chat with the LLM about results (the chat is where scouting reports live; the app no longer shows them in the dossier).
- **The data-mining team** — operate the offline pipeline and the analysis scripts, and evaluate the system as a course deliverable (the grader evaluates the Flutter app alongside the ML methodology and results, which the analysis scripts present; see [Analysis scripts](#45-analysis-scripts)).

External systems:

| External system | Relationship |
| --- | --- |
| Kaggle "Football Data from Transfermarkt" dataset | Source of truth for raw data. The ingest stage downloads it through Kaggle's API at a pinned dataset version and writes its tables as Parquet under `ml/data/`; the version and snapshot hash are recorded per run ([ADR-010](#adr-010-kaggle-api-with-a-pinned-dataset-version-over-a-manually-downloaded-snapshot)). |
| ggml-org/llama.cpp project | Source of the llama.cpp server container image used for local LLM inference. |
| Quantized GGUF model weights | Downloaded manually from the public GGUF repository `bartowski/Qwen_Qwen3.5-9B-GGUF`: the file `Qwen_Qwen3.5-9B-Q5_K_M.gguf` (Q5_K_M quant, 6,782 MiB — 7.11 GB / 6.62 GiB) is stored in `llms/models/` as `Qwen3.5-9B-Q5_K_M.gguf`, which is the path the `inference-chat` service serves (`LLAMA_ARG_MODEL`). The running system never fetches model weights at runtime. |

Provisioning assumptions: model weights are provisioned manually — an engineer downloads the chosen GGUF file into `llms/models/` before the stack starts, and the `inference-chat` service mounts that directory. The runtime intent from docs/CONTEXT.md ("Windows environments") is satisfied either through Docker Desktop with WSL2 GPU passthrough (CUDA variant of the llama.cpp image) or by accepting CPU-only inference latency where no GPU is available; nothing in the architecture depends on which.

A headline product claim from docs/CONTEXT.md ("EXTRAS") is that scouting data never leaves the club's servers. The architecture honors this because all inference runs through a local llama.cpp process; no third-party LLM API is called.

## 3. Architecture overview

The system is a small containerized stack: a Flutter frontend, a FastAPI backend, one PostgreSQL instance with two schemas, one local LLM server, and an offline batch pipeline that shares a Python package with the backend. Analysis scripts produce the report's figures and tables from the pipeline's outputs.

The ML pipeline is shown as a black box here by design. Its internals are deferred to [docs/ML_ARCHITECTURE.md](ML_ARCHITECTURE.md).

## 4. Components

### 4.1 Flutter frontend

- **Responsibility:** The user experience. Web-focused Flutter application for searching players, viewing valuations and undervaluation findings, exploring clusters/archetypes, and chatting with the LLM (the Flutter app does not browse stored scouting reports). The UX is a deliberate product feature, not a demo shell.
- **Technology:** Flutter Web (Dart), with the Flutter SDK pinned to an exact version in `pubspec.yaml` and `pubspec.lock` committed; all pins date from project kickoff and are bumped only via explicit dependency-bump commits. Targets web desktop/browser form factors (served on port `80` in Docker Compose).
- **Interfaces/contracts:** Consumes the backend's REST API. The OpenAPI spec that FastAPI generates is the contract of record; the Flutter HTTP client is written by hand against that spec ([ADR-025](#adr-025-a-hand-written-dart-http-client-against-the-openapi-contract)). Talks only to the backend: the frontend never reaches the database, pipeline, or LLM server directly.
- **Structure:** layered MVVM with `ChangeNotifier` ViewModels and `provider` ([ADR-023](#adr-023-layered-mvvm-with-changenotifier-and-provider-in-the-flutter-app)), `go_router` with the URL as the explorer's state ([ADR-024](#adr-024-go_router-with-the-url-as-the-explorers-state)), bundled fonts and flags ([ADR-026](#adr-026-bundled-fonts-and-flags-no-third-party-requests-from-the-client)), one dossier breakpoint ([ADR-027](#adr-027-desktop-layouts-from-1280-to-1920-px-with-one-dossier-breakpoint)), and the backend URL compiled in at build time ([ADR-029](#adr-029-the-api-base-url-is-a-build-time-define)). Commands and layout are in [frontend/AGENTS.md](../frontend/AGENTS.md).

### 4.2 FastAPI backend

- **Responsibility:** Serves all use cases to the frontend over REST: player search and valuation results, undervaluation findings, replacement recommendations served read-only from the pipeline-published `replacements` table (the "at least 3 profitable replacements per elite asset" expectation from docs/CONTEXT.md section 5 — see [Data flow](#51-batch-flow)), live "what-if" scoring of a synthetic player profile against the active model artifacts (delivery priority 3, [ADR-007](#adr-007-delivery-priority-under-the-course-deadline)), the cluster/archetype explorer, scouting report retrieval and generation triggers, and LLM chat relay. It enforces the LLM call limits (timeouts, concurrency, context budget — defined in `docs/ML_ARCHITECTURE.md`) and degrades the LLM-dependent routes when the inference service is unavailable (see [Cross-cutting concerns](#9-cross-cutting-concerns)).
- **Technology:** FastAPI on uvicorn (Python, with the versions aligned across components, [Artifact contract](#43-delphos_ml-shared-package)), with Pydantic schemas shared with `delphos_ml` types. Organized as routers/services/schemas per feature, following the layout the team used in hyperwrite-ai.
- **Interfaces/contracts:**
  - **In:** REST from the Flutter client, described by the generated OpenAPI spec (see [API surface sketch](#6-api-surface-sketch)).
  - **Out:** reads the `analytics` schema and reads/writes the `app` schema in PostgreSQL through the API database role, resolving the active model run through `analytics.model_runs` (see [Artifact contract](#43-delphos_ml-shared-package)); loads joblib model artifacts from `artifacts/` via the `delphos_ml` package for live inference (`POST /players/what-if`); calls the llama.cpp server over OpenAI-compatible HTTP for report generation and chat, passing model outputs and player metrics as context within the limits defined in `docs/ML_ARCHITECTURE.md`.

### 4.3 delphos_ml shared package

- **Responsibility:** The single Python library both the backend and the pipeline import. It contains data schemas/types (shared Pydantic models), model-loading code, and the scoring functions used for inference. Batch training and batch scoring live behind the pipeline's CLI; interactive scoring is exposed as ordinary importable functions.
- **Technology:** Python package living in `ml/` (see [Repository layout](#repository-layout)). Targets scikit-learn, pandas, and Pydantic (with the versions aligned across components, [Artifact contract](#43-delphos_ml-shared-package)). Dependencies are added as stages need them; today the package depends on cloudpickle, joblib, kagglehub, numpy, pandas, pyarrow, pydantic, pydantic-settings, scikit-learn, scipy, threadpoolctl, and typer. Model artifacts are serialized with joblib.
- **Interfaces/contracts:** The backend imports it to load trained joblib artifacts from `artifacts/` and score on demand (live inference, e.g. "what-if" re-scoring of a hypothetical player). The pipeline imports it for batch training and batch scoring. This dual-mode requirement — batch inference by the pipeline and live inference by the API from the same artifacts — is a core architectural constraint, which is why the package is shared rather than duplicated.

**Artifact contract** — the publish/load boundary this package enforces:

- Each publish writes `artifacts/<model_run_id>/` containing the trained model, the preprocessor, and a `manifest.json` with the ordered feature names, the scikit-learn, joblib, cloudpickle, numpy, scipy, threadpoolctl and `delphos_ml` versions, the pinned Kaggle dataset version and snapshot hash, and a training-config reference. The exact manifest and training-config fields are defined in `docs/ML_ARCHITECTURE.md`.
- Exactly one `model_runs` row has status `active`; both the publish stage and the backend resolve the "current model" through it (see [Publish/activation protocol](#44-offline-ml-pipeline)).
- `delphos_ml.load_model()` refuses to load an artifact whose recorded scikit-learn, joblib, cloudpickle, numpy, scipy, threadpoolctl or `delphos_ml` version differs from the installed one. The serialized payload depends on that whole stack, not on scikit-learn alone: fitted estimators hold `numpy` arrays, joblib pickles through `cloudpickle`, scikit-learn imports numpy, scipy and threadpoolctl at import time, and the preprocessor classes the artifact unpickles into belong to `delphos_ml` itself.
- **The version check is a compatibility guard, not an integrity control.** `manifest.json` lives inside `artifacts/<model_run_id>/`, so anyone who can rewrite the artifact can rewrite the manifest to match. Loading a joblib artifact is arbitrary code execution by design: artifacts are trusted by provenance only, and only `publish` writes them, on the analyst's machine. To turn tampering into a load failure rather than silent code execution:
  - `publish` records a SHA-256 of **every** file it writes into `artifacts/<model_run_id>/` — the model, the preprocessor and `manifest.json` — in the same `model_runs` row. The manifest is hashed too because it carries the ordered feature names and the dataset provenance: an unhashed manifest can be rewritten to reorder or reselect model inputs and silently move the served numbers.
  - `load_model(run_id, expected_sha256=<mapping the caller read from `model_runs`>)` **fails closed**: an absent mapping is a refusal, not a skip. `delphos_ml` does not query the database; the caller that already resolved the `model_runs` row passes the digests in.
  - The check is not check-then-use. The loader reads each file's bytes once, hashes that buffer, and unpickles from the same buffer (`joblib.load(io.BytesIO(buffer))`), so the bytes that were verified are the bytes that execute. Hashing a path and then opening it is a race the targeted adversary wins.
- `load_model(run_id)` validates the run id before joining it to the artifacts root: `re.fullmatch(r"[A-Za-z0-9_-]{1,64}", run_id)` must succeed (`fullmatch`, not `match` with `$`, which tolerates a trailing newline), and the resolved path must stay inside the resolved `artifacts/` root. A run id is a path component and is never trusted as one.
- Each Python component is its own uv project with its own lockfile ([ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace)): `ml/` today, `backend/` when it lands. Their direct dependency versions are manually aligned on the same versions: cloudpickle 3.1.2, joblib 1.6.0, kagglehub 1.0.2, numpy 2.5.4, pandas 3.1.0, pyarrow 26.0.0, pydantic 2.14.1, pydantic-settings 2.16.0, scikit-learn 1.9.1, scipy 1.18.1, threadpoolctl 3.7.0, typer 0.27.3. Every package in that list is a direct dependency of `delphos-ml`, so each one is declared in `ml/pyproject.toml` and resolved by its lockfile. The `>=` bounds in each `pyproject.toml` are lower bounds: the exact versions are the ones in that project's `uv.lock`. A component that unpickles artifacts must resolve the same versions; the seven versions the manifest records (scikit-learn, joblib, cloudpickle, numpy, scipy, threadpoolctl and `delphos_ml`) are refused at load time when they differ, and the remaining aligned versions (pandas, pyarrow, pydantic, pydantic-settings, kagglehub, typer) are kept equal by discipline, because no manifest field covers them. Joblib unpickling therefore cannot drift between the pipeline that wrote the artifacts and the API that reads them only as long as the versions stay aligned; without one shared lockfile this alignment is a discipline, not a guarantee (accepted risk, recorded in ADR-013).

### 4.4 Offline ML pipeline

> Internal design (algorithms, features, evaluation) is deferred to [docs/ML_ARCHITECTURE.md](ML_ARCHITECTURE.md). This section covers only its place in the software architecture.

- **Responsibility:** Batch ingestion and publishing. Runs the stages ingest → clean → transform → train → evaluate → publish, producing trained models and publishing curated player data, predictions, cluster assignments, valuation residuals, replacement candidates, and an inefficiency analysis into the database.
- **Technology:** Python with scikit-learn and pandas, orchestrated as Typer CLI stages: `uv run delphos-pipeline <stage>`, one command per stage, each writing to `ml/data/<stage>/`. `uv run delphos-pipeline all` runs the implemented stages in order and stops at the first failure. It is a batch pipeline, not a long-running service: it runs manually, on demand, or on a schedule via Docker (the `pipeline` compose profile). It is never on the request path.
- **Interfaces/contracts:**
  - **In:** the ingest stage downloads the Kaggle dataset through Kaggle's API at a pinned dataset version, with no credentials required for this public dataset ([ADR-010](#adr-010-kaggle-api-with-a-pinned-dataset-version-over-a-manually-downloaded-snapshot)).
  - Ingest is a text-only faithful copy of the source; typing and cleaning happen in `clean` ([ADR-012](#adr-012-ingest-stores-source-columns-as-text-typing-happens-in-clean)).
  - **Out:** the stages write their outputs as Parquet under `ml/data/`, and `publish` is the only stage that writes to PostgreSQL ([ADR-008](#adr-008-parquet-files-between-pipeline-stages-postgresql-only-at-publish)). The pipeline writes trained model artifacts (joblib) into `artifacts/<model_run_id>/` per the [Artifact contract](#43-delphos_ml-shared-package), and publishes curated player data, predictions, cluster assignments, valuation residuals, replacement candidates, and the inefficiency analysis into the `analytics` schema through the pipeline database role (writes `analytics` only).
  - The `evaluate` stage produces an inefficiency-analysis output (`inefficiency_analysis`), published alongside predictions. Minimal acceptance for this output: at least one hypothesis test with a reported statistic and significance over transfer-fee vs predicted-value residuals, presented by the analysis scripts (see [Analysis scripts](#45-analysis-scripts)) and summarized in the app. Which tests and which statistics are defined in `docs/ML_ARCHITECTURE.md`.

**Publish/activation protocol.** `publish` is transactional from the API's point of view:

1. Write the new artifacts to a fresh `artifacts/<model_run_id>/` directory first ([Artifact contract](#43-delphos_ml-shared-package)).
2. Insert this run's `model_runs` row, then bulk-load the curated player data (profiles and performance metrics served by `GET /players*`) and all result rows — predictions, clusters, replacements, inefficiency analysis — in a single database transaction, with `model_run_id` on every row.
3. In that same transaction, demote the previously active run and mark this run `active`; the previous run's result rows stay intact.

The API filters its reads on the active run and includes the `model_run_id` in responses that carry model-derived values. A crash before step 3 leaves the prior run's artifacts, rows, and active pointer untouched, so a crashed run never corrupts what the API serves. A crash after step 1 leaves an orphan `artifacts/<model_run_id>/` directory, which is safe to delete.

### 4.5 Analysis scripts

- **Responsibility:** One script per analysis in the top-level `analysis/` directory: exploratory data analysis, the statistical demonstration of market inefficiency (at least one hypothesis test with reported statistic and significance over transfer-fee vs predicted-value residuals; the test selection is defined in `docs/ML_ARCHITECTURE.md`), and the model-comparison figures. Each script's module docstring states its input, its output, and its single responsibility ([ADR-009](#adr-009-analysis-scripts-over-jupyter-notebooks)).
- **Technology:** Python 3.13, executed from the `ml/` uv project through its `analysis` dependency group ([ADR-014](#adr-014-analysis-scripts-run-in-the-ml-uv-project-through-a-dependency-group)). Scripts import `delphos_ml` instead of re-implementing algorithms.
- **Interfaces/contracts:** Reads the pipeline's Parquet outputs under `ml/data/`. Writes figures and tables to `analysis/output/` (gitignored, regenerable) and nothing to the database. The scripts are not part of the deployed stack.

### 4.6 LLM inference service

- **Responsibility:** The only separate AI process. It is delivery priority 4 ([ADR-007](#adr-007-delivery-priority-under-the-course-deadline)) and is built only if time permits. Serves two features: (a) AI-generated natural-language scouting reports that translate model results into executive prose, and (b) an interactive chat where the user converses about scouting results. For chat, the backend relays the conversation and includes model outputs and player metrics as context, and the model reaches the published data through the backend's read-only tools ([ADR-015](#adr-015-in-process-function-calling-for-the-chat-tool-layer)).
- **Technology:** llama.cpp server (`ghcr.io/ggml-org/llama.cpp:server-cuda`, with the plain `server` image as the CPU-only variant) serving a quantized Qwen GGUF model from a mounted `llms/models/` directory, over an OpenAI-compatible HTTP API. The image is referenced by tag because the same variable (`LLAMA_ARG_IMAGE`) selects the CPU variant; the digest of the image in use on the analyst host is `sha256:e8d36f4dc2a72a1df323748f6219c9dd11f662f7cb3b06a6b2916c9bf3866d89` (build `b9294`). The shipped model is **Qwen3.5-9B** in the **`Q5_K_M`** quant, selected in [ADR-017](#adr-017-qwen35-9b-in-q5_k_m-as-the-served-model); the model file is provisioned manually into `llms/models/` and the running system never fetches weights at runtime.
- **The GPU must be handed to the container.** The compose service declares `gpus: all`, which needs Docker Compose 2.30 or newer, Docker Engine 25 or newer and the NVIDIA Container Toolkit (bundled in Docker Desktop). Without the request the image does not fail: it logs `no usable GPU found, --gpu-layers option will be ignored` and serves on the CPU, roughly an order of magnitude slower than the 40-60 t/s the report path assumes. With the request, a host with no NVIDIA card cannot create the container at all, so the CPU variant uses `docker-compose.cpu.yml`, which resets the key. The check after start-up is that the startup log lists `CUDA0` and that the model buffer is on the device, not that the container is healthy.
- **The container is hardened and bounded.** It runs with a read-only root, no capabilities, `no-new-privileges` and a 64 MiB writable `/tmp`, and it is limited to `mem_limit: 12g`, `pids_limit: 256` and `restart: unless-stopped`: it parses model files in-process, it is reachable from the host, and a peer must not be able to exhaust the host's RAM or leave the service down.

- **Exposure.** The service is published on the host at the address named by `DELPHOS_INFERENCE_PUBLISH_IP` (default `127.0.0.1`, so loopback-only) and the host port named by `DELPHOS_INFERENCE_PUBLISH_PORT` (default `8081`); the container's own port stays `8080`, which is what the compose network reaches at `http://inference-chat:8080`. Setting the address to the host's ZeroTier address exposes the OpenAI-compatible API to that network — the deployment shape [docs/LLM_FALLBACK_PLAN.md](LLM_FALLBACK_PLAN.md) describes — without opening it to the LAN. `0.0.0.0` must not be used: the llama.cpp API is unauthenticated, so the exposure surface is exactly the interface named here. That is a policy the tooling does not enforce, and the address must name an interface that is up and holds that address when the container starts, or the bind fails.
- **Serving configuration:** the compose service sets the model binding and the serving flags explicitly:

  | Setting | Value | Why |
  | --- | --- | --- |
  | `LLAMA_ARG_MODEL` | `/models/Qwen3.5-9B-Q5_K_M.gguf` | The file inside the mounted directory; a file path, not a repository id. |
  | `LLAMA_ARG_ALIAS` | derived from `DELPHOS_LLM_MODEL_NAME` | The id the server reports for the loaded model. The request is routed by that id, so it must equal the id the backend sends; compose derives it from the same variable, which is why the two cannot drift ([ADR-022](#adr-022-one-model-id-derived-on-both-sides)). |
  | `LLAMA_ARG_CTX_SIZE` | `32768` | The total KV pool and the chat history budget. |
  | `LLAMA_ARG_N_PARALLEL` | `4` | Concurrent chat sessions. |
  | `LLAMA_ARG_KV_UNIFIED` | `on` | **Load-bearing, not decoration** — see below. |
  | `LLAMA_ARG_N_GPU_LAYERS` | `99` | Offload the whole model to the GPU. |
  | `LLAMA_ARG_FLASH_ATTN` | `on` | Flash attention on the Blackwell card. |
  | `LLAMA_ARG_JINJA` | `on` | The server refuses a `tools` request without it. |
  | `LLAMA_ARG_REASONING` | `auto` | The server decides per request; the backend sends `enable_thinking` per request. |
  | `LLAMA_ARG_CACHE_TYPE_K` / `_V` | `q8_0` | Never 4-bit: a 4-bit K cache collapses hybrid prefill by ~20x on this model. |

  **`LLAMA_ARG_KV_UNIFIED: "on"` is the one flag that fails quietly if it is wrong.** `--ctx-size` is the *total* KV pool, and llama.cpp divides it across the slots unless the cache is unified: with `n_parallel: 4` and the cache divided, each slot gets `32768 / 4 = 8192` tokens, the chat budget does not fit, and long conversations are silently truncated with no error in the log. Setting `n_parallel` explicitly is what disables the unified cache, so the flag has to be set explicitly too. The check is the startup line `n_ctx_slot = 32768`; anything smaller means the context is still being divided.
- **Health check:** `["CMD", "curl", "-f", "http://localhost:8080/health"]` with `start_period: 60s` (the model load from a cold page cache dominates startup). `curl`, not `python3`: the llama.cpp server image installs only `libgomp1`, `curl` and `ffmpeg`, so a `python3` healthcheck fails with "executable file not found" and the container stays permanently unhealthy. `GET /health` returns 200 only when the model is loaded, so the check verifies the model, not the port.
- **Interfaces/contracts:** In: OpenAI-compatible HTTP (`/v1/chat/completions` and related endpoints) from the backend, which is the only caller inside the system — no in-system client calls it directly. The service is also published on a host address ([ADR-031](#adr-031-the-inference-server-is-published-on-a-named-host-address)), so a peer machine on that network can call it directly; the API is **unauthenticated**, and a published peer therefore bypasses the backend's question cap, token caps, concurrency semaphore and tool allowlist. This service is the system's sole LLM provider: no external LLM API is called anywhere in the system. Out: none.

LLM call parameters — timeouts, concurrency limits, context budget and assembly rules, and model/quant selection — are defined in `docs/ML_ARCHITECTURE.md` §3.19 and, for the configuration keys, in [Cross-cutting concerns](#9-cross-cutting-concerns). The backend enforces those limits on every call and degrades the LLM-dependent routes when this service is unavailable (see [Cross-cutting concerns](#9-cross-cutting-concerns)).

### 4.7 PostgreSQL

- **Responsibility:** The single datastore for both pipeline outputs and application data.
- **Technology:** `postgres:16` (plain image; pgvector is not required by the current scope — see [Data storage design](#7-data-storage-design) and [Future work](#11-future-work)). One instance, two schemas (`analytics`, `app`), access separated by database roles.
- **Interfaces/contracts:** The pipeline writes `analytics` only (pipeline role). The backend reads both schemas and writes `app` only (API role). No other component touches the database. See [Data storage design](#7-data-storage-design) for details.


`ml/data/` and `analysis/output/` are gitignored and regenerable.

`artifacts/` is **gitignored**, not Git LFS. Artifacts are fully regenerable by running the pipeline, and reproducibility is handled by pinning dependencies and recording the dataset snapshot and training configuration alongside each run (see [Cross-cutting concerns](#9-cross-cutting-concerns)). Git LFS would add tooling overhead for a course project without buying reproducibility we do not already have.

`docker-compose.yml` sits at the repo root, which differs from hyperwrite-ai's `backend/`-local placement. The reason: this stack spans backend, LLM inference, database, and pipeline — none of which is subordinate to `backend/` — so the single compose file (one per stack, per hyperwrite-ai convention) belongs at the root.

Conventions adopted from hyperwrite-ai: one `docker-compose.yml` per stack; `.env` gitignored with `.env.example` committed; environment variables for all configuration (see [Cross-cutting concerns](#9-cross-cutting-concerns)); Conventional Commits; branch naming `type/part-of-project/what-you-are-doing` (e.g. `feat/backend/player-search`).

## 5. Data flow

### 5.1 Batch flow

The pipeline publishes results; the API serves them; the frontend displays them. This is the primary path for valuations, undervaluation findings, cluster assignments, and replacement recommendations. Replacement recommendations are computed by the pipeline at publish time, not by the API on request: the backend serves the published `replacements` rows read-only through `GET /players/{id}/replacements`. The endpoint returns up to 3 ranked candidates: exactly 3 when 3+ qualifying candidates exist, otherwise fewer with an explicit "no qualifying replacement" reason, never padded. The "elite asset" definition and the athletic-equivalence/similarity metric behind candidate ranking are defined in `docs/ML_ARCHITECTURE.md`.

```mermaid
flowchart LR
    DS["Kaggle API<br/>pinned dataset version"] --> P[offline ML pipeline<br/>ingest - clean - transform<br/>train - evaluate - publish]
    P -->|joblib| ART[(artifacts/)]
    P -->|"Parquet stage outputs"| DATA[("ml/data/")]
    P -->|"curated players, predictions, clusters,<br/>residuals, replacements, inefficiency analysis"| AN[("analytics schema")]
    AN -->|read| API[FastAPI backend]
    API -->|REST| UI[Flutter app]
```

The stages exchange Parquet files under `ml/data/`, and only `publish` writes to `analytics`.

### 5.2 Live inference flow

The backend scores on demand using the published artifacts, for interactive use cases such as re-scoring a hypothetical ("what-if") player profile. This path is exposed as `POST /players/what-if`: it accepts a synthetic player profile and returns the live-computed fair value and undervaluation flag from the loaded joblib artifacts via `delphos_ml`, with the `model_run_id` of the artifacts used. The what-if input schema and the batch-vs-live equivalence guarantee are defined in `docs/ML_ARCHITECTURE.md`. This flow is delivery priority 3 ([ADR-007](#adr-007-delivery-priority-under-the-course-deadline)).

```mermaid
flowchart LR
    UI[Flutter app] -->|REST request| API[FastAPI backend]
    API -->|load via delphos_ml| ART[(artifacts/ joblib models)]
    API -->|score| API
    API -->|REST response| UI
```

### 5.3 LLM report and chat flow

The backend assembles context (model outputs, player metrics) and calls the llama.cpp server. Two flows share that call but nothing else: separate prompts, separate code paths, separate context budgets, and different failure behaviour.

**Report flow.** `POST /reports/generate` builds the fact card from the published `analytics` rows of the active model run, asks the model for a structured draft in which every number is a `{fact_ref}` placeholder, substitutes the verified numbers back into the prose, checks the result against the fact card, and persists the report with its provenance. The report is **not streamed**: the numeric-fidelity check needs the complete prose, so a streamed report would show the reader text whose numbers were not yet checked ([ADR-018](#adr-018-reports-are-non-streaming-chat-may-stream)).

**The stored report is HTML.** `app.reports.content` holds three `<p>` paragraphs with `<strong>`/`<em>` marks, as the design preview renders them with `innerHTML`; the Flutter app no longer renders reports (see the [ADR-028](#adr-028-report-html-rendered-with-flutter_widget_from_html_core-superseded-in-the-frontend) amendment of 2026-11-15), so any client that does must sanitize the markup. Every interpolated value is escaped for an HTML text context (`html.escape(..., quote=True)`): the player's name, club and league come from the database and are as untrusted there as the model's prose. The markup the backend emits is not escaped, so the deterministic renderer stays byte-identical to the design preview's reference. The numeric verifier masks HTML entities before it scans, so an escaped apostrophe (`&#x27;`) cannot read as the number 27.

**Grounding.** The model may not write a number: every numeric claim in the prose is substituted from the fact card. A drafted replacement candidate is bound to the card's candidate **by name**, never by its position in a list, and its prose resolves against **that candidate's own cells only** — a draft that reorders its candidates, or cites a key the candidate does not own, is an error that falls back to the deterministic renderer rather than publishing a wrong number about a real person.

**Deterministic fallback.** Every generation failure — a timeout, an HTTP error, an empty completion, a rejected draft, or prose that fails numeric verification after one repair attempt — falls through to the deterministic renderer, which produces the same three executive sections from the same fact card with no LLM involved ([ADR-019](#adr-019-the-deterministic-renderer-is-the-fallback-and-the-quality-baseline)). The endpoint therefore returns **200 with a correct report** whenever the facts exist: an LLM outage degrades the report, it does not fail the request. The report's provenance says which path produced it.

**The cache.** A stored report answers a request only when it was produced by a configured model and prompt configuration: the key is `(player_id, model_run_id, report_type, llm_model, prompt_version)`, and the model id is matched against the **candidate set** of the configured endpoints — the primary's id plus the fallback's id when it is set — so the stored id is always one of the lookup's candidates ([ADR-021](#adr-021-the-report-cache-key-includes-the-model-and-the-prompt-version), [ADR-033](#adr-033-the-backend-falls-back-to-a-second-inference-endpoint-over-zerotier)). The endpoint is not part of the key: the provenance names the model that wrote the text, not the machine that served it. The deterministic row the last fallback wrote is served for at most **15 minutes**: a downed LLM then costs a cached answer instead of a 120-second wait per request, and a recovered LLM replaces the fallback instead of leaving the player on the template forever.

```mermaid
flowchart LR
    UI[Flutter app] -->|POST /reports/generate| API[FastAPI backend]
    API -->|fact card = published analytics rows<br/>of the active model run| CARD[fact card]
    CARD -->|prompt + json schema| LLM[llama.cpp server<br/>Qwen3.5-9B Q5_K_M]
    LLM -->|draft with fact_ref placeholders| API
    API -->|numeric verification| CHECK[verified prose]
    CARD -.->|fallback on any failure| DET[deterministic renderer]
    CHECK --> APP[(app schema<br/>source, llm_model,<br/>prompt_version)]
    DET --> APP
    APP -->|report text + provenance| UI
```

**Chat flow.** `POST /chat` runs a bounded tool loop: the model selects one of five typed read-only tools, the backend executes it in-process against the `analytics` schema, and the result goes back to the model ([ADR-015](#adr-015-in-process-function-calling-for-the-chat-tool-layer)). Chat **may stream** (`text/event-stream`) when the client asks for it; a failure after the headers are sent ends the stream with an `error` event, and a failed turn is not persisted ([ADR-018](#adr-018-reports-are-non-streaming-chat-may-stream)).

The loop is bounded on every axis that a hostile or confused model could push: the question is capped at 2,000 characters by the request schema, the prompt is trimmed to the server's context size and **re-trimmed before every completion** (the tool payloads the loop appends are not part of the first budget), the model reply is parsed by a bounded, `RecursionError`-safe parser that treats an unparsable reply as a plain answer, and the number of concurrent LLM calls is capped by a semaphore sized to the inference server's parallel slots. Every tool execution opens **its own** pooled connection: a connection is never held across an LLM wait, so a slow model cannot occupy a slot of the shared pool for the length of a turn.

```mermaid
flowchart LR
    UI[Flutter app] -->|POST /chat| API[FastAPI backend]
    API -->|OpenAI-compatible HTTP<br/>system prompt + history + question| LLM[llama.cpp server]
    LLM -->|tool call or answer| API
    API -->|read-only query| AN[(analytics schema)]
    AN -->|capped result| API
    API -->|answer, streamed or returned| UI
    API -.->|complete exchanges only| APP[(app schema)]
```

Report and chat metadata (which `model_run_id`, and for a report which model and prompt version, produced it) is persisted in the `app` schema; the generated text flows through the API to the client. v1 records a single implicit actor: report and chat rows either omit actor columns or carry one shared actor, and `shortlists` is one shared list. Identity columns arrive with the deferred authentication work ([Future work](#11-future-work)).

## 7. Data storage design

One PostgreSQL instance holds two schemas with separate owners. Access separation is enforced by database roles, not by convention:

| | `analytics` | `app` |
| --- | --- | --- |
| Owner | Pipeline | Backend |
| Written by | Pipeline role only | API role only |
| Read by | API role | API role |
| Contents | Curated player data (profiles and performance metrics), predictions, cluster assignments, valuation residuals, replacement candidates, inefficiency analysis, model/run metadata | User data: saved shortlists, scouting report records, chat session/message metadata |

Illustrative tables (design intent, not exhaustive): `analytics` holds a curated players table (the profiles and performance metrics served by `GET /players*`, keyed by player and `model_run_id`), a `predictions` table (fair value, residual, undervaluation flag, keyed by player and `model_run_id`), a `clusters` table, a `replacements` table (computed at publish, keyed by target player and `model_run_id`, holding up to 3 ranked candidates per target with similarity score and cost data; exactly 3 when 3+ qualify, otherwise fewer with an explicit "no qualifying replacement" reason, never padded), the inefficiency-analysis output, and a `model_runs` table recording each publish. `app` holds `shortlists`, `reports` (text plus the `model_run_id` that produced them, and the report's provenance: `source` — `llm` or `deterministic` —, `llm_model` and `prompt_version`, added by migration `0004`), and `chat_sessions` / `chat_messages`. Raw and intermediate data live as Parquet under `ml/data/` ([ADR-008](#adr-008-parquet-files-between-pipeline-stages-postgresql-only-at-publish)).

Schema changes are managed by Alembic with one migration head per schema (`analytics`, `app`); each head is applied by that schema's owning role — pipeline role for `analytics`, API role for `app`. The role/schema bootstrap SQL implied by ADR-002 is committed as migration `0001`, so role enforcement lives in reviewable migrations rather than manual setup. Migrations run as the one-shot `migrate` compose step before the backend starts (see [Deployment topology](#8-deployment-topology)).

The two-database-server alternative was considered and rejected: it adds operational overhead (two backups, two upgrades, cross-DB queries needed for reports) without buying real isolation, since one course project controls both roles. Role separation within one instance is sufficient. See [Decisions and tradeoffs](#10-decisions-and-tradeoffs).

The base image is plain `postgres:16`; pgvector is not adopted because no current feature requires vector search. If semantic retrieval over reports is ever added, switching to the pgvector-enabled image of the same major version is a drop-in change ([Future work](#11-future-work)).

## 8. Deployment topology

Everything runs under Docker Compose via a single root `docker-compose.yml` (scalable and reproducible per the team's decision). Named network; one named volume for DB data (`pgdata`); bind mounts for the host directories `./ml/data`, `./artifacts`, and `./llms/models`, so the host-side analysis scripts and the manually provisioned GGUF files are visible to the containers; healthchecks with `depends_on: condition: service_healthy` throughout, plus a one-shot `migrate` step that the backend waits on (`service_completed_successfully`).

| Service | Image / build | Ports | Volumes | Depends on |
| --- | --- | --- | --- | --- |
| `frontend` | `frontend/Dockerfile`: a Flutter 3.47.5 build stage runs `flutter build web --no-web-resources-cdn --csp` with the `DELPHOS_API_URL` build arg, and `nginxinc/nginx-unprivileged:1.30.6-alpine` (both base images pinned by digest) serves the static files on `8080` with an SPA fallback, the cache policy and the security headers (`frontend/nginx/`). The container runs read-only with tmpfs for `/tmp`, `/var/cache/nginx` and `/etc/nginx/conf.d`, all capabilities dropped and `no-new-privileges` | `127.0.0.1:80` on the host to `8080` (HTTP) | none (tmpfs only) | `backend` (service_healthy) |
| `backend` | FastAPI app (`backend/`, uvicorn) | `8000` | `./artifacts` bind mount (read-only) | `db` (service_healthy), `migrate` (service_completed_successfully) |
| `db` | `postgres:16` | `5432` internal; published on `0.0.0.0` at `DELPHOS_DB_PORT` (the default `5432`) for local tooling — a wider exposure than the inference port, and one ADR-031 records as a follow-up | `pgdata` named volume | — |
| `migrate` | Alembic migrations (`migrations/`; one-shot, exits when done) | none | — | `db` (service_healthy) |
| `inference-chat` | `ggml-org/llama.cpp` server image (CUDA variant; CPU fallback), with `gpus: all` so the CUDA build actually sees the card | `8080` internal; published on the host at `DELPHOS_INFERENCE_PUBLISH_IP:DELPHOS_INFERENCE_PUBLISH_PORT` (`127.0.0.1:8081` by default; set the address to the host's ZeroTier address to expose it to that network) | `./llms/models` bind mount (GGUF files, read-only) | — |
| `pipeline` | ML pipeline (`ml/`, compose profile `pipeline`) | none | `./artifacts` bind mount (read-write), `./ml/data` bind mount (read-write, Parquet stage outputs) | `db` (service_healthy), `migrate` (service_completed_successfully) |

Notes:

- `pipeline` is gated behind the compose profile so it never starts with the stack; it is invoked as `docker compose --profile pipeline run pipeline <stage>` (or on a schedule outside the always-on services).
- `migrate` runs both Alembic heads (one per schema) as their owning database roles and exits; the backend starts only after it succeeds, so schema migrations are applied before any request is served.
- The backend deliberately does not depend on `inference-chat`. An LLM outage degrades only `/reports/*` and `/chat`, and every other route serves normally: `/reports/generate` falls back to the deterministic rendering and still returns 200, while `/chat` returns a documented "LLM unavailable" problem response.
- The `inference-chat` healthcheck verifies that the model is actually loaded (a server-side model check), not merely that the process is listening.
- All configuration comes from `.env` (gitignored; `.env.example` committed and authoritative for the key list; see [Cross-cutting concerns](#9-cross-cutting-concerns)).
- The pipeline needs outbound HTTPS to Kaggle during ingest only.
- Only `publish` writes to the database. Under compose, every pipeline stage still starts `db` and `migrate` through `depends_on`; outside compose, the earlier stages need only a Python environment (ADR-008).
- The LLM service loads its GGUF model from the mounted models directory; the model file itself is not baked into the image.
- The inference service runs with a read-only root filesystem, no capabilities and `no-new-privileges`, with a writable `/tmp` only, because it parses model files in-process and is reachable from the host. The model directory is mounted read-only as well. It is bounded with `mem_limit: 12g`, `pids_limit: 256` and `restart: unless-stopped`.
- The `inference-chat` service needs Docker Compose 2.30 or newer, Docker Engine 25 or newer and the NVIDIA Container Toolkit (bundled in Docker Desktop) for `gpus: all`. On a host without an NVIDIA card, `docker-compose.cpu.yml` is used alongside the base file (`docker compose -f docker-compose.yml -f docker-compose.cpu.yml up -d inference-chat`), which removes the GPU request, together with `LLAMA_ARG_IMAGE=server` and a CPU-sized model.

**Dev vs prod.** In development, `backend` runs uvicorn with reload, `frontend` runs via `flutter run` against the compose backend, the `db` port may be exposed for local tooling, and the LLM service may run on the CPU variant. In production-shaped deployments, the frontend is a static build, no dev reloads, and the DB and LLM ports are published only on the addresses named in `.env` — the LLM one by [ADR-031](#adr-031-the-inference-server-is-published-on-a-named-host-address) — never on `0.0.0.0`. The `backend` service is currently published on `0.0.0.0` without authentication, which is a wider exposure than either of those; ADR-031 records it as the follow-up that matters most. Both modes use the same compose file; the differences are driven by `.env`, by profiles and by the `docker-compose.cpu.yml` override, not by divergent files.

## 9. Cross-cutting concerns

- **Configuration and secrets.** All configuration is environment variables read from `.env`, which is gitignored; `.env.example` at the repository root documents every key for every component. The pipeline reads the variables below through pydantic-settings. Precedence is real environment variables, then the nearest `.env`, then the defaults. The project root, used to resolve a relative `DELPHOS_DATA_DIR`, is the nearest directory at or above the working directory that contains `uv.lock`, which in this repository is `ml/` ([ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace)). The `.env` lookup walks upward from the working directory, first hit wins, and stops after the parent of the project root. With the working directory at `ml/` (where the dev commands run), the lookup checks `ml/.env` and then `<repo root>/.env`; the documented location is the repo root, beside `.env.example`. A `.env` above the repository root is never read. With no `uv.lock` at or above the working directory, only the working directory itself is checked. An invalid value exits with code 1 and a message naming the variable. `.env.example` mirrors this table, which is the complete list: the pipeline's, the backend's, the frontend's build-time key and the inference server's keys.

A non-empty value must be an `http`/`https` URL whose host is an **IP literal inside `DELPHOS_LLM_FALLBACK_PEER_CIDR`** — a hostname is refused, because it could resolve anywhere and DNS would defeat the allowlist — with **no userinfo** (`http://user:pass@host` is rejected), **no query string**, **no fragment** and no whitespace; an invalid value fails the settings load with a message naming the variable. Loopback, link-local, unspecified, multicast and reserved addresses are refused whatever the range says. The host should be a **different machine** than the backend's: pointing it at this host's own published address is a second path to the same process, and buys no availability (the backend warns when it sees that). The endpoint is unauthenticated; the compensating control is a ZeroTier ACL pinning the published port to the peer. |
| `DELPHOS_LLM_FALLBACK_MODEL_NAME` | `""` (empty) | Model id sent in the request body to the fallback endpoint. An empty value means "the same model as `DELPHOS_LLM_MODEL_NAME`", and that is the id the peer must report: the comparison is **strict** in both cases, so a peer that serves another model is **refused**, never warned about, and its prose can never be stored as the club's model output. The report cache accepts a report written by **either** configured model id, so a report produced by one endpoint answers the next request even when the other one produced it; the provenance names the model, not the machine ([ADR-033](#adr-033-the-backend-falls-back-to-a-second-inference-endpoint-over-zerotier)). |
| `DELPHOS_LLM_FALLBACK_TIMEOUT_SECONDS` | `60.0` | Timeout of one call to the fallback endpoint (0 < value ≤ 600). The remote link is slower than the local one, and the bound keeps one request from waiting the primary's budget twice. |
| `DELPHOS_LLM_FALLBACK_PEER_CIDR` | `10.0.0.0/8` | The range the peer's address must sit in. The backend refuses a fallback whose address is outside it, so a public host or an address outside the ZeroTier range cannot receive the club's prompts; the range must not be empty while a fallback URL is set, because without it there is no allowlist, and it must be **inside a private range** (`10/8`, `172.16/12`, `192.168/16`) — a range that admits the public internet would void the allowlist. The default is the whole RFC1918 `10/8` block — the range ZeroTier managed networks usually sit in — so an operator must narrow it to the peer's actual subnet. The honest limits: a wrong address **inside** the allowed range still passes the check, and a host inside it that answers as an OpenAI-compatible server passes the probe too; the ZeroTier ACL is what pins the address to the peer ([ADR-033](#adr-033-the-backend-falls-back-to-a-second-inference-endpoint-over-zerotier)). |
| `DELPHOS_LLM_PRIMARY_PROBE_SECONDS` | `5.0` | Timeout of the reachability probe the backend makes against an endpoint before a call (0 < value ≤ 60). The probe is one cheap `GET` of the model list, and it carries no prompt and no credential; **both** endpoints are probed with it, so a dead or wrong peer address never receives a prompt. The endpoint counts as serving only when it answers HTTP 200 with a JSON body carrying a model list, and the verdict is cached for five seconds ([ADR-033](#adr-033-the-backend-falls-back-to-a-second-inference-endpoint-over-zerotier)). |
| `DELPHOS_API_URL` | `http://localhost:${DELPHOS_API_PORT:-8000}` in compose, `http://localhost:8000` in a plain build | Backend URL compiled into the Flutter web build with `--dart-define=DELPHOS_API_URL=...`; the compose `frontend` service passes it as a build arg, so a change needs a rebuild, and also as a runtime variable, from which `frontend/nginx/15-delphos-api-origin.envsh` derives the origin for the CSP `connect-src` (a value that is not an `http(s)://host[:port]` URL stops the container). The browser calls the API from the user's machine, so it is the backend's host URL, not `http://backend:8000` ([ADR-029](#adr-029-the-api-base-url-is-a-build-time-define)). |
| `LLAMA_ARG_MODEL` | `/models/Qwen3.5-9B-Q5_K_M.gguf` | The GGUF file the `inference-chat` service serves, inside the mounted `./llms/models` directory. Override it to run the CPU variant of the model. Read by `docker-compose.yml`, not by the application. |
| `LLAMA_ARG_IMAGE` | `server-cuda` | Image tag of the llama.cpp server: `server-cuda` is the CUDA build, `server` the CPU build, selected with the same compose file. Read by `docker-compose.yml`. |
| `LLAMA_ARG_ALIAS` | derived from `DELPHOS_LLM_MODEL_NAME` | The id llama.cpp reports for the loaded model. The request is **routed by that id**, so it must equal the id the backend sends; compose derives it from `DELPHOS_LLM_MODEL_NAME`, so the two cannot drift apart ([ADR-022](#adr-022-one-model-id-derived-on-both-sides)). |
| `DELPHOS_INFERENCE_PUBLISH_IP` | `127.0.0.1` | Host address the `inference-chat` service publishes its port on. `127.0.0.1` keeps the server local-only; the host's ZeroTier address exposes it to that network ([ADR-031](#adr-031-the-inference-server-is-published-on-a-named-host-address)). Read by `docker-compose.yml` for the bind, and by the backend, which warns when a fallback names this host's own published address. |
| `DELPHOS_INFERENCE_PUBLISH_PORT` | `8081` | Host port the `inference-chat` service publishes. The container's own port stays `8080`; only the host side is remapped. Read by `docker-compose.yml`, not by the application. |

**What the compose deployment actually forwards.** The `backend` service forwards `DELPHOS_LLM_API_URL`, `DELPHOS_LLM_MODEL_NAME`, the five fallback keys (`DELPHOS_LLM_FALLBACK_API_URL`, `DELPHOS_LLM_FALLBACK_MODEL_NAME`, `DELPHOS_LLM_FALLBACK_TIMEOUT_SECONDS`, `DELPHOS_LLM_FALLBACK_PEER_CIDR`, `DELPHOS_LLM_PRIMARY_PROBE_SECONDS`) and `DELPHOS_INFERENCE_PUBLISH_IP` to the container; every other `DELPHOS_LLM_*` key in `.env` therefore has **no effect** there, and the container uses the code defaults, which are the values in this table. In particular `DELPHOS_LLM_MAX_CONCURRENT_LLM_CALLS` cannot be tuned through `.env` in the compose deployment: the cap is the default `4`, which matches `LLAMA_ARG_N_PARALLEL: 4`, so the behaviour is correct, but the knob is only tunable where the backend runs outside compose (a local `uv run uvicorn`) or after the key is added to the service's `environment` block. `DELPHOS_INFERENCE_PUBLISH_PORT` is read by `docker-compose.yml` alone: no application reads it, and setting it in the backend's environment has no effect. `DELPHOS_INFERENCE_PUBLISH_IP` is read by both: compose binds the published port to it, and the backend compares it with the fallback's host to warn about a fallback that is only a second path to the same process.

A relative `DELPHOS_DATA_DIR`, including the default, requires a `uv.lock` at or above the working directory; otherwise the run exits 1 with a message naming `DELPHOS_DATA_DIR`. A container must therefore include `uv.lock` or set an absolute `DELPHOS_DATA_DIR`.
- **Reproducibility of model artifacts.** `artifacts/` is gitignored, so reproducibility rests on three things: pinned dependency versions (per-component lockfiles with manually aligned direct dependency versions, as the [Artifact contract](#43-delphos_ml-shared-package) requires; joblib-unpickling drift is guarded by that pinning discipline, an accepted risk recorded in [ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace); the Flutter SDK pinned in `pubspec.yaml` with `pubspec.lock` committed; all pins date from project kickoff and are bumped only via explicit dependency-bump commits), the Kaggle dataset `version` and `snapshot_sha256` recorded at ingest in `ml/data/ingest/_snapshot.json` together with `tool_versions` (kagglehub and pyarrow), and training configuration persisted with each run in `analytics.model_runs`. Anyone can re-run the pipeline and obtain equivalent artifacts.
- **Versioning of published results.** Every published row carries the `model_run_id` that produced it, and reports record the model version used: `app.reports` carries the report's provenance (`source`, `llm_model`, `prompt_version`), and the report cache is keyed on the model and the prompt version as well as on the model run ([ADR-021](#adr-021-the-report-cache-key-includes-the-model-and-the-prompt-version)). Exactly one run is `active` at a time; the API reads only the active run and includes the `model_run_id` in responses that carry model-derived values ([Publish/activation protocol](#44-offline-ml-pipeline)). Re-publishing a new model does not silently rewrite historical results already surfaced to users.
- **Error handling at service boundaries.** The backend is the only component that talks to clients, and it translates failures at its boundaries into RFC 9457 problem responses (`application/problem+json` with `type`, `title`, `status`, `detail`, and `trace_id`), defined once as a shared Pydantic model behind a global exception handler. Expected problem types, by endpoint group: *missing artifact* and *stale artifact* (any model-derived read and `/players/what-if`), *LLM unavailable* (`/chat` — the rest of the API keeps working during an LLM outage), *mid-stream failure* (streamed chat responses, after the 200 headers were already sent), and *not found* (`/players/{id}` and other id lookups). The report path is not in that list: `/reports/generate` degrades to the deterministic rendering and still returns 200, and only a failure of the renderer itself is an error ([ADR-019](#adr-019-the-deterministic-renderer-is-the-fallback-and-the-quality-baseline)). The pipeline fails fast per stage and leaves the previously published results in place; `publish` is the last stage and flips the active pointer only in its final transaction ([Publish/activation protocol](#44-offline-ml-pipeline)), so a crashed run does not corrupt what the API serves.
- **Testing.** v1 scope is unit tests with pytest: fixtures for artifact loading and parametrized scoring cases, covering the `delphos_ml` load/score paths (`ml/tests/`) and the API route logic (`backend/tests/`). The golden batch-vs-live equivalence check, contract tests, OpenAPI drift checks, and CI are explicitly out of v1 scope — listed in [Future work](#11-future-work), not as v1 commitments.
- **CORS for the Flutter client.** The Flutter web app runs on a different origin than the API. Allowed origins are configured via an env var consumed by FastAPI's CORS middleware.

## 10. Decisions and tradeoffs

Short ADR-style records. The decisions below are settled as recorded, for context; when a decision changes, a later ADR supersedes the earlier one and the superseded record stays in place for history ([ADR-011](#adr-011-python-tooling-with-a-uv-workspace) is superseded by [ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace)).

### ADR-001: FastAPI (Python) over Go for the backend

- **Context:** The backend must serve REST to the Flutter client and perform live inference from scikit-learn artifacts.
- **Decision:** FastAPI on Python.
- **Alternatives:** Go (rejected), Django (heavier than needed).
- **Consequences:** The backend imports `delphos_ml` directly and reuses Pydantic types across ML and API code; one language across backend and ML; OpenAPI documentation is generated for free and becomes the Flutter client's contract. The tradeoff is runtime performance versus Go, which does not matter at this scale.

### ADR-002: One Postgres instance with two schemas over two databases

- **Context:** Pipeline-owned analytics data and backend-owned app data both need storage with separated write access.
- **Decision:** One PostgreSQL instance, `analytics` and `app` schemas, separation enforced by two database roles (pipeline writes `analytics` only; API reads both and writes `app` only).
- **Alternatives:** Two database servers (rejected: operational overhead — separate backups, upgrades, connection pools — without additional meaningful isolation for a single-team system; cross-database joins for report generation would become awkward).
- **Consequences:** One backup, one upgrade path, and the pipeline/API contract is expressed entirely in the `analytics` schema. Access separation is only as strong as role enforcement; the bootstrap SQL that creates the roles and schemas is committed as Alembic migration `0001`, so enforcement is applied from reviewable migrations rather than manual setup.

### ADR-003: Offline batch pipeline + shared package over a tabular-inference microservice

- **Context:** Valuations, clusters, and residuals could be precomputed by a long-running inference service or by batch runs.
- **Decision:** A batch pipeline publishes results to the database and model artifacts to `artifacts/`; the backend imports the shared `delphos_ml` package for the interactive "what-if" cases that cannot be precomputed.
- **Alternatives:** A separate always-on inference microservice (rejected: another deployable and network hop for a workload that is fundamentally batch-shaped; the dataset updates on the order of the Kaggle snapshot, not per-request).
- **Consequences:** The common query path is a database read (fast, simple). Interactive scoring shares one code path (`delphos_ml`) with batch training, eliminating train/serve skew. The cost is that precomputed results refresh only when the pipeline runs, which matches the data's update cadence.

### ADR-004: Local llama.cpp (GGUF) as the sole LLM provider

- **Context:** Scouting data is confidential, and the "EXTRAS" section of docs/CONTEXT.md makes privacy a product claim.
- **Decision:** A local llama.cpp server with a quantized Qwen GGUF model is the system's only LLM provider; no hosted or external API is called at any point.
- **Alternatives:** Hosted API only (rejected: breaks the "data never leaves the club's servers" claim and adds a third-party dependency); a hosted adapter behind a common interface, e.g. Gemini (rejected: even behind a common adapter interface it reintroduces egress, API keys, and a second provider path that undermines the privacy claim the product leads with; the team confirmed llama.cpp-only).
- **Consequences:** The privacy claim is total — all inference runs on the club's hardware. Model quality and updates depend entirely on the locally chosen GGUF model. No API keys or LLM egress to manage. This decision deliberately narrows the Gemini option docs/CONTEXT.md originally allowed.

### ADR-005: Flutter over Streamlit or React

- **Context:** The frontend is a graded deliverable and a stated product feature; it must present search, valuations, clusters, reports, and chat.
- **Decision:** Flutter Web (100% web target).
- **Alternatives:** Streamlit (rejected: fastest to build but reads as a demo shell, contrary to the product intent, and constrains the UX); React (rejected: viable, but the team selected Flutter Web for a cohesive, custom-styled analytical dashboard UX deployed as a static web build in Docker Compose).
- **Consequences:** The team commits to Dart and Flutter Web tooling; in return the app is a genuine front-office web product surface rather than a demo shell.

### ADR-006: Docker Compose as the deployment unit

- **Context:** The system spans frontend, backend, database, LLM inference, and an offline pipeline; the team wants it scalable and reproducible.
- **Decision:** One root `docker-compose.yml` runs the whole stack; the pipeline runs under a compose profile.
- **Alternatives:** Kubernetes (rejected: operational overkill for a course project); ad-hoc local installs (rejected: not reproducible across the team's machines and the grader's).
- **Consequences:** `docker compose up` reproduces the full stack anywhere with Docker; one file per stack stays true to the hyperwrite-ai convention. Scaling beyond one host would require moving to an orchestrator, which is out of scope.

### ADR-007: Delivery priority under the course deadline

- **Context:** Final delivery is on 2026-11-25. As of 2026-10-17 there is no code, two people work jointly on one track, and the architecture describes more than may fit.
- **Decision:** Build and protect, in this order: (1) the offline ML pipeline end to end, including the inefficiency analysis and replacements; (2) a minimal demo, meaning FastAPI plus Flutter covering player search, valuation, and replacements, together with the PostgreSQL and compose pieces they need; (3) live what-if (`POST /players/what-if`); (4) the LLM reports and chat (`/reports/*`, `/chat`, the `inference-chat` service). Under time pressure, cut from the bottom: 4 first, then 3. Items 1 and 2 are never cut.
- **Alternatives:** Build every component to the same depth (rejected: on a single track that risks having no finished ML results); drop the app (rejected: the app is the system's demo and is evaluated alongside the ML work, see [System context](#2-system-context)).
- **Consequences:** The LLM and what-if designs stay in this document as the target, marked with their priority.
- **Amendment (2026-11-04):** With Priority 1 (entire ML pipeline + PostgreSQL publishing) and Priority 2's backend read endpoints completed ahead of schedule at the opening of Week 6, the team promoted AI-generated scouting reports (`/reports/generate`) from stretch scope into the active delivery plan for Week 7 alongside the Flutter app.

### ADR-008: Parquet files between pipeline stages; PostgreSQL only at publish

- **Context:** Section 7 had `analytics` hold raw and staging tables, so every stage needed PostgreSQL, the roles, Alembic, and compose from day one.
- **Decision:** Ingest, clean, transform, train, and evaluate exchange data as Parquet files under `data/`, which is gitignored and regenerable. `publish` is the only stage that writes to PostgreSQL. Its single transaction loads the curated player data the API serves (profiles and performance metrics for `GET /players*`) together with the result rows, all carrying `model_run_id`.
- **Alternatives:** Staging tables in `analytics` (rejected: ties all ML work to database setup that is only needed for the demo).
- **Consequences:** ML work needs only a Python environment. The `analytics` schema holds only what the API serves. The analysis scripts read the same Parquet files. The publish/activation protocol keeps its three steps, with curated player data added to step 2's bulk load.

### ADR-009: Analysis scripts over Jupyter notebooks

- **Context:** The team decided on plain Python scripts with no notebooks, and the docs had described a graded notebook mirror.
- **Decision:** A top-level `analysis/` directory holds one script per analysis (exploratory data analysis, the statistical inefficiency demonstration, model-comparison figures). Each script's module docstring states its input, its output, and its single responsibility. Scripts read the pipeline's Parquet outputs under `data/` and import `delphos_ml` instead of re-implementing algorithms. They write figures and tables to `analysis/output/` (gitignored, regenerable), write nothing to the database, and are not part of the deployed stack.
- **Alternatives:** A Jupyter notebook mirror (rejected: hidden cell state and mixed responsibilities make it hard to tell what each piece does).
- **Consequences:** The inefficiency demonstration and model-comparison figures are produced as files under `analysis/output/`; there is no notebook deliverable.

### ADR-010: Kaggle API with a pinned dataset version over a manually downloaded snapshot

- **Context:** The dataset was previously planned as a manually downloaded local snapshot with no recorded version.
- **Decision:** The ingest stage downloads the dataset through Kaggle's API (kagglehub) at a pinned dataset version and writes its tables as Parquet under `data/ingest/`. This public dataset needs no credentials; if Kaggle ever requires them, kagglehub reads `KAGGLE_*` variables from the process environment or `~/.kaggle`, not from the pipeline's `.env` settings. The dataset version and snapshot hash are recorded per run (`docs/ML_ARCHITECTURE.md` §3.1).
- **Alternatives:** Manual download (rejected: unrecorded version and a manual step); committing data files (rejected: bloats the repo and duplicates the source of truth).
- **Consequences:** Ingest needs outbound network access, and refreshing the data means deliberately bumping the pinned version. The "data never leaves the club's servers" claim is unaffected because ingest only downloads.

### ADR-011: Python tooling with a uv workspace

- **Context:** Section 11 listed the Python version, dependency tool, CLI framework, Kaggle client, configuration mechanism, and `ml/` layout as undecided, and the Artifact contract requires one shared constraint set.
- **Decision:** Python 3.13, pinned in `.python-version` (`requires-python = ">=3.13,<3.14"`). A uv workspace with a virtual root: the root `pyproject.toml` has no `[project]` table, lists `members = ["ml"]`, and holds a `dev` dependency group (pytest, ruff) with their configuration. Exactly one `uv.lock` at the root is the shared constraint set of the [Artifact contract](#43-delphos_ml-shared-package). The member `ml/` is the distribution `delphos-ml` (import name `delphos_ml`) in a src layout, built with `uv_build`. Dependencies are kagglehub as the Kaggle client, pyarrow, pydantic, pydantic-settings, and Typer; pandas returns with the `clean` stage. The CLI is a Typer console script, `delphos-pipeline` (`delphos_ml.pipeline.cli:app`). Each stage is one module with one entry function whose docstring is its `--help` text, and a stage exits 0 on success and 1 on an expected failure with `<stage> failed: <reason>` on stderr. Stage outputs go to `data/<stage>/`. Configuration uses pydantic-settings with the `DELPHOS_` prefix ([Cross-cutting concerns](#9-cross-cutting-concerns)). The locked direct versions are kagglehub 1.0.2, pyarrow 26.0.0, pydantic 2.14.1, pydantic-settings 2.16.0, and typer 0.27.3, with pytest 9.1.1 and ruff 0.17.1 for development.
- **Alternatives:** A root project instead of a virtual root (rejected: it would need an empty package just to list the members); pip-tools and poetry (rejected); argparse instead of Typer (rejected); a flat layout instead of src (rejected); `raw/interim/processed` directories instead of `data/<stage>/` (rejected); python-dotenv instead of pydantic-settings (rejected).
- **Consequences:** One `uv.lock` is the shared constraint set. `backend/` joins as a workspace member that uses the same lock, and the analysis scripts' dependencies go in a root dependency group. The "all" runner arrives with the second stage; until then `ingest` is the only command.
- **Status:** superseded by [ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace) on 2026-10-18; retained for history.

### ADR-012: Ingest stores source columns as text; typing happens in clean

- **Context:** The first ingest implementation let pandas infer column types. An audit found that this changed the source text ("007" became 7, "700000.000" became 700000.0, "True" became a bool), silently renamed duplicate headers, and put typing work inside ingest.
- **Decision:** Ingest is a faithful copy. Every column of every `data/ingest/*.parquet` is Arrow `string` and holds the exact CSV field text, so "007", "True", "700000.000", "NA", "null", and "-" are kept as they are. Only an unquoted empty field becomes null. A quoted empty field (`""`) stays an empty string, because the source writes empty strings that way and keeps them distinct from null. Blank lines are skipped in multi-column files, but in a single-column file an empty line is an unquoted empty field and becomes a null row; a final trailing newline never adds a row. Quoted values may span lines, and a UTF-8 BOM is stripped. Each file is streamed in 16 MiB blocks with pyarrow, so memory does not grow with file size. A header with duplicate, empty, or whitespace-only names fails the run, as do an empty file, invalid UTF-8, and ragged rows; each failure prints one `ingest failed: <reason>` line and exits 1. The output swap retries each rename 3 times and restores the previous output on failure. An existing `ingest/` without `_snapshot.json` is never replaced. Concurrent runs are not supported.
- **Alternatives:** pandas type inference (rejected: it changed the text form, renamed duplicate headers, and mixed typing into ingest).
- **Consequences:** `clean` must cast every column it uses explicitly and record the rules in `docs/ML_ARCHITECTURE.md` §3.5. Memory stays bounded by streaming.

### ADR-013: Per-component uv projects over a root uv workspace

- **Context:** [ADR-011](#adr-011-python-tooling-with-a-uv-workspace) set up a root uv workspace with one shared `uv.lock` when `ml/` was the only Python component. With a single member, the virtual root `pyproject.toml` and the root lockfile were overhead, and the backend had not arrived yet. The [Artifact contract](#43-delphos_ml-shared-package) still requires the Python components to agree on the versions that read and write joblib artifacts.
- **Decision:** Each Python component is its own uv project. `ml/` owns its `pyproject.toml` (project metadata, the `dev` dependency group, and the pytest and ruff configuration), its `uv.lock`, and its `.python-version` (Python 3.13). The root `pyproject.toml` and root `uv.lock` are removed. `.env.example` stays at the repository root as the global configuration-key list for every component (see [Cross-cutting concerns](#9-cross-cutting-concerns)). `backend/` gets its own uv project and lockfile when it lands. Joblib-unpickling drift is held off by manually aligned direct dependency versions across the lockfiles; the list of those versions is maintained in [Artifact contract](#43-delphos_ml-shared-package) so that the two documents cannot drift apart. The project-root anchor (the nearest `uv.lock` at or above the working directory) now resolves to `ml/`, so a relative `DELPHOS_DATA_DIR` defaults stage outputs to `ml/data/<stage>/`.
- **Alternatives:** Keep the root workspace with the single shared lock (rejected: it was overhead for a single Python component, and scoping tooling per module was preferred).
- **Consequences:** Each component installs, locks, tests, and lints independently, from its own directory. Version alignment between `ml/` and the future `backend/` is a manual discipline rather than a lockfile guarantee: a backend install that resolves a different joblib-relevant version can fail to unpickle the pipeline's artifacts, and this accepted risk is recorded here. Configuration stays global (one `.env.example` at the repo root); the `.env` lookup (nearest `.env` at or above the working directory, first hit wins) is bounded by the lockfile-based project-root anchor: the walk stops after the project root's parent, so a `.env` above the repository root is never read, and with no `uv.lock` at or above the working directory only the working directory itself is checked.

### ADR-014: Analysis scripts run in the `ml/` uv project through a dependency group

- **Context:** [ADR-009](#adr-009-analysis-scripts-over-jupyter-notebooks) places analysis scripts in the top-level `analysis/` directory and requires them to import `delphos_ml` and read `ml/data/<stage>/`. When [ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace) dissolved the root uv workspace, it gave `ml/` its own uv project and left the Python environment for `analysis/` unspecified.
- **Decision:** Analysis scripts run in the `ml/` uv project (`uv run python ../analysis/<script>.py` from `ml/`). Plotting and statistical libraries that the deployed `delphos_ml` wheel does not need (`matplotlib` 3.11.2, `scipy` 1.18.1, `seaborn` 0.13.2) live in an `analysis` dependency group in `ml/pyproject.toml`, listed alongside `dev` in `[tool.uv] default-groups` so `uv sync` installs both. `pandas` 3.1.0 joins `ml/`'s runtime dependencies because `clean` and later pipeline stages use it directly.
- **Amendment (2026-10-31):** `scipy` 1.18.1 moved from the `analysis` group to the runtime dependency set, because scikit-learn imports scipy at import time and the deployed wheel needs it whatever the analysis group says. `numpy` 2.5.4, previously only an implicit transitive dependency of `pandas`, is now declared explicitly, because the serialized artifacts depend on the numpy ABI. `matplotlib` and `seaborn` remain analysis-only, which was the point of this ADR.
- **Alternatives:** Give `analysis/` its own `pyproject.toml` and `uv.lock` (rejected: creates a second lockfile and virtual environment that must install `delphos_ml` from `../ml`, and shifts the `uv.lock` project-root anchor away from `ml/`, which breaks the default `DELPHOS_DATA_DIR` resolution to `ml/data/`); put plotting libraries in `[project].dependencies` (rejected: pulls `matplotlib` and `seaborn` into the `delphos_ml` runtime package that the backend container imports).
- **Consequences:** One `uv sync` inside `ml/` prepares the pipeline, tests, linter, and analysis scripts. Running scripts from `ml/` resolves `DELPHOS_DATA_DIR` to `ml/data/` without extra environment variables and keeps plotting packages out of `delphos_ml`'s runtime dependencies.
- **Scope note (2026-11-08):** the LLM evaluation harness lives in the same top-level `analysis/` directory and runs from `ml/` through the same `analysis` dependency group, but it reads the **published database** rather than `ml/data/<stage>/`. The report and chat case sets are built from published players — they need `valuation_status` and `cluster_id`, and `ml/data/transform/player_seasons.parquet` (36 columns) carries neither: `valuation_status` is published to `analytics.fct_player_predictions` and `cluster_id` to `analytics.fct_clusters`, both of which exist only after `train` and `publish`. The experiments therefore query the `analytics` schema read-only, through the same path the backend uses, so the cases are the published players the product actually serves. This is the one documented exception to the rule that analysis scripts read the pipeline's Parquet outputs.

### ADR-015: In-process function calling for the chat tool layer

- **Context:** The chat agent must let the model query the published `analytics` data. Three shapes were available: an MCP server the model talks to, free-form text-to-SQL, and typed tools the backend executes itself. The tool set is five read-only queries (`search_players`, `get_player_profile`, `get_player_valuation`, `get_player_replacements`, `get_cluster_summary`), and every one of them already exists as a repository function.
- **Decision:** The tool layer is **in-process function calling**. The model selects a tool and fills typed arguments; the backend validates the arguments, executes the tool against the `analytics` schema through the API role, and feeds a bounded, read-only result back to the model. The model never writes a query. A tool failure, an unknown tool name and a bad argument are typed errors the model can read and retry, never exceptions to the client. Results are capped (a fixed list limit, a fixed JSON payload bound), and the loop is capped at four tool iterations.
- **Alternatives:** An MCP server (rejected: a second service, a second deployment and a protocol boundary for five read-only queries that are already repository functions, in a stack that already runs the app, the database, the migration step and the inference service); free-form text-to-SQL (rejected: a grammar constrains syntax, not semantics, so an 8B-class model joining nine tables produces wrong-but-valid SQL, which is more dangerous than a hallucinated number because it looks authoritative); one generic "query the database" tool (rejected: the same failure mode with less observability — a typed tool's arguments can be validated and its errors can be named).
- **Consequences:** No new compose service, no new dependency, and the tool layer is testable offline against fixtures. The price is that the guards are ours to write: the iteration cap, the result caps, the argument validation, the context-budget trim, the concurrency cap and the bounded reply parser. The number of tools is a design parameter rather than an afterthought, because every tool's schema is re-sent on every turn and every iteration of every conversation. Four of those guards are about resources rather than correctness, and they are what keeps the chat path inside the inference server's budget: the prompt is trimmed to the server's context size and re-trimmed before every completion (the tool payloads the loop appends are not in the first budget); the number of concurrent LLM calls is capped by a semaphore sized to the server's parallel slots, so a burst queues instead of saturating the GPU; every tool execution opens its own pooled connection, so a slow model never holds a pool slot for the length of a turn; and the model's reply is parsed by a bounded, `RecursionError`-safe parser that treats an unparsable reply as a plain answer, so a hostile payload cannot become a 500.

### ADR-016: A direct OpenAI-compatible client with Pydantic schemas, without an agent framework

- **Context:** The feature plan chose PydanticAI (C4) to express the report's structured output and to own the chat loop. The shipped backend instead talks to llama.cpp through one async `httpx` client (`services/llm_client.py`).
- **Decision:** The backend talks to the inference service over its OpenAI-compatible HTTP API through a single client module, and expresses every contract in Pydantic. The report's structured output is requested with llama.cpp's native `response_format` JSON-schema constraint — which the server converts into a GBNF grammar and enforces at the token level — and is validated by the `report_schema` models, whose prose fields reject any digit outside a `{fact_ref}` placeholder, so a fabricated number is unrepresentable rather than detected. The chat tool loop is a bounded loop written directly against that client, parsing the model's tool call and feeding typed tool errors back to it. The drafted report is then rendered by the backend: every placeholder is substituted with the fact card's formatted value, the prose and the substituted values are escaped for an HTML text context because the stored report is injected with `innerHTML`, and a placeholder that does not resolve — including one cited in a candidate's sentence that the candidate does not own — is an error that sends the request back to the deterministic renderer rather than publishing a broken or wrong sentence.
- **Alternatives:** PydanticAI (planned in the feature plan, **not in the shipped code**: it wraps the same llama.cpp mechanisms, but its structured-output support is selected by a case-sensitive model-name profile, and the loop the feature needs is small enough that the framework's abstraction was not needed — the backend declares no agent-framework dependency); llama.cpp's native `tools` parameter for the chat path (not implemented: the shipped chat protocol is an explicit JSON tool call in the reply, which is what the prompt and the parser implement, and the tool-calling experiments that would decide a change have not been run); a hand-written HTTP client per feature (rejected: two clients means two timeout, sampling and error-mapping policies that would drift).
- **Consequences:** The backend image gains no framework dependency, and the request path has no framework-specific behaviour. The price is ownership: the loop, the retry semantics and the schema request are ours to maintain, and moving to a framework later is a rewrite of the chat loop and the generation call rather than a configuration change. The backend owns the rendering of the model's draft as well as the request: the substitution, the escaping and the per-candidate scoping are backend rules, and a draft that breaks them is discarded instead of published.

### ADR-022: One model id, derived on both sides

- **Context:** llama.cpp routes a request by the model id in the request body, and the server reports the loaded model under its own alias. The backend sent `DELPHOS_LLM_MODEL_NAME` while the inference service served its own `LLAMA_ARG_ALIAS`: two settings, with separate defaults and no relationship between them. When they disagreed, every LLM request failed to resolve the model — and because the report path falls back to the deterministic renderer on **any** LLM failure, the symptom was silent: the endpoint answered 200 with a correct report, and the LLM path never ran at all. This was a critical deployment defect, found in review, not a theoretical risk.
- **Decision:** There is **one** variable, `DELPHOS_LLM_MODEL_NAME`, and the compose file derives the server's alias from it: `LLAMA_ARG_ALIAS: ${DELPHOS_LLM_MODEL_NAME:-qwen/qwen3.5-9b}`. The backend and the server therefore cannot drift, and overriding the variable in `.env` moves both sides at once. The stored provenance and the cache key read that same id from the same request-scoped `Settings` object ([ADR-021](#adr-021-the-report-cache-key-includes-the-model-and-the-prompt-version)), and the id the server reports back is logged when it differs from the requested one. **Amendment (2026-11-17):** with the fallback endpoint, the provenance may name the fallback's model id, and the cache lookup accepts both configured ids ([ADR-033](#adr-033-the-backend-falls-back-to-a-second-inference-endpoint-over-zerotier)); the derivation itself is unchanged, and the fallback's id has its own setting.
- **Alternatives:** Two independent variables with a documented "keep them equal" rule (rejected: the rule is unenforceable in a deployment, and it is exactly how the defect shipped); a startup check that compares the two and refuses to boot (rejected as a substitute for the derivation, not as a complement: it would turn a silent wrong behaviour into a loud one, but it still leaves two variables to keep in sync, whereas a derived value cannot drift); a fixed alias on the server and a fixed id in the backend (rejected: it forbids the documented CPU-variant override of the model id).
- **Consequences:** The model id is a single setting, overridable in one place, and the two sides cannot disagree. The failure mode this removes is the dangerous one: a silent fallback that looks like a working feature, which no test of the report's *content* would ever catch. The manual check stays cheap — `curl http://inference-chat:8080/v1/models` must report the id the backend sends — and it stays in the manual verification list of the feature plan.

### ADR-017: Qwen3.5-9B in Q5_K_M as the served model

- **Context:** [ADR-004](#adr-004-local-llamacpp-gguf-as-the-sole-llm-provider) fixed llama.cpp with a quantized Qwen GGUF as the system's only LLM provider, and the 2026-11-04 decision ([docs/ML_ARCHITECTURE.md](ML_ARCHITECTURE.md) §3.18) named a 3B-class model. The team superseded that choice on 2026-11-08: the chat feature needs an agentic model, and a September-2024 instruct model is not one.
- **Decision:** Serve **Qwen3.5-9B** as GGUF in the **`Q5_K_M`** quant (6,782 MiB — 7.11 GB / 6.62 GiB — for the provisioned file) on the 16 GB host. The quantisation rules are: tool calling floors at `Q5_K_M`/`Q4_K_M`, because argument-level fidelity breaks first and the tool path is unforgiving; report prose uses `Q5_K_M`–`Q6_K`, because quantization artifacts show in long-form prose as repetition and broken clauses; `IQ3_S` is never used (documented garbage output on this card), and neither is `Q3_K_M`/`Q2_K` for the report. The KV cache stays at `q8_0` and is never 4-bit. Variants: `Q4_K_M` (5.68 GB) for an 8 GB host, Qwen3.5-4B `Q4_K_M` (2.74 GB) for CPU-only, and Granite 4.2-8B as the documented independent fallback.
- **Alternatives:** gpt-oss-20b (rejected: 11.62 GB of weights leave 2-3 GB for KV on a 16 GB card, its 128K context does not fit alongside them, it cannot run on 8 GB at all, and its Harmony channel format is an integration cost — it is a documented over-budget option, not a default); Gemma 4 E4B (rejected: the best memory profile of the set, but Tau2 42.2 against Qwen3.5-9B's 79.1, and a documented Blackwell-specific decode pathology on this exact card); Granite 4.2-8B as the primary (rejected as primary, kept as the fallback: it documents a non-thinking mode that Qwen3.5's toggle does not reliably provide); Qwen2.5-3B-Instruct / Llama-3.2-3B-Instruct (rejected: the superseded choice, and both predate the agentic-training era).
- **Consequences:** The decisive scores are the agentic ones — BFCL-V4 66.1 and TAU2 79.1, with IFEval 91.5 for instruction following — and the KV footprint is what makes the deployment fit: 16,384 B/token, about 512 MiB for a 32K pool, so four concurrent slots cost almost nothing in VRAM once the cache is unified. The model file is provisioned manually into `llms/models/`; the running system never fetches weights at runtime.
- **Amendment (2026-11-16):** the repository and the file are now fixed: `bartowski/Qwen_Qwen3.5-9B-GGUF`, file `Qwen_Qwen3.5-9B-Q5_K_M.gguf`, stored in `llms/models/` as `Qwen3.5-9B-Q5_K_M.gguf` (the path `LLAMA_ARG_MODEL` serves). Measured on disk, the file is **6,782 MiB (7.11 GB / 6.62 GiB)** and its SHA-256 is `a686d88ec1e6881f9bf161526826cd6d6874b7f0e80e0f79acf6144a132c5d7e`, which is the upstream digest. The 6.58 GB the original decision quoted does not match it, and the quant choice is unchanged. §2 repeats the repository, the file name and the size for the reader who lands there first; this amendment is the decision record for them.

### ADR-018: Reports are non-streaming; chat may stream

- **Context:** The first description of the report flow said the response is "returned or streamed". The two features have different shapes: a report is a fixed three-section document that is checked before it is shown, and a chat answer is a conversational turn whose first token is what the user waits for.
- **Decision:** `POST /reports/generate` returns a complete body. `POST /chat` streams when the client requests it (`stream: true`), answering with `text/event-stream`. Mid-stream failure semantics apply to chat only: once the 200 headers are sent the status cannot change, so a failure terminates the stream with an `error` event and the client renders the partial text and the failure marker; a failure before the first byte is an ordinary problem response. A failed chat turn is not persisted, so `app.chat_messages` holds complete exchanges only.
- **Alternatives:** Streaming both (rejected: the report's numeric-fidelity check needs the complete prose, so a streamed report would put text in front of the reader before its numbers were checked); streaming neither (rejected: the chat's perceived latency is its first token, and the answer is short); streaming the report and checking afterwards (rejected: the failure mode is a wrong number already on screen).
- **Consequences:** The "mid-stream failure" problem type belongs to the chat path only. The report path's guarantee is stronger and simpler: the response is complete, verified, and either the model's or the deterministic rendering's.

### ADR-019: The deterministic renderer is the fallback and the quality baseline

- **Context:** A report that depends on a local 9B model depends on a GPU, a model file and a warm server. The report surface is a product feature, and its failure mode — the reader gets a 503 — is the one the product cannot absorb.
- **Decision:** The report has a **deterministic renderer**: the same three executive sections, the same bold labels and the same number formatting, built from the same fact card with no LLM involved. It is used in two ways. It is the **fallback** for every generation failure — timeout, HTTP error, empty completion, or prose that fails numeric verification after one repair attempt — and the endpoint then returns **200 with a correct report**, recording `source = 'deterministic'`. It is also the **baseline** the LLM output is measured against: if the model's prose is not better than the template for a given player, the template is what is served.
- **Alternatives:** 503 on an LLM outage (rejected: the report is the deliverable; degrading to a correct, if templated, report keeps the product working while the provenance says exactly what happened); serving the template without recording it (rejected: the report list would then show a report that no model wrote, and the cache would not know which text it holds); skipping the renderer and relying on retries (rejected: a retry does not fix an absent GPU).
- **Consequences:** `app.reports.source` records which path produced each report, and the report's own text carries the difference. The deterministic renderer is also the floor the LLM path has to clear before it ships, which makes it the most valuable module to test. Because the stored report is HTML that the client injects with `innerHTML`, the renderer escapes **every interpolated value** — the names, clubs and leagues come from the database and are as untrusted there as model prose — while the markup it emits itself is left alone, so the output stays byte-identical to the design preview's reference. The numeric verifier masks HTML entities before it scans, so an escaped apostrophe (`&#x27;`) is not read as the number 27.

### ADR-020: The Spanish vocabulary lives in a dependency-free `delphos_domain` distribution

- **Context:** The product's Spanish copy — positions, sub-positions, league names, valuation statuses and cluster archetypes — lived only in the frontend's JavaScript. The backend had English cluster names and raw codes, and the database has no vocabulary columns at all. Two copies of a taxonomy that must agree is exactly the drift this decision exists to prevent, because the report and the UI would name the same archetype differently, in two languages, in two files.
- **Decision:** The vocabulary moves into **its own dependency-free distribution**, `delphos_domain` (`ml/src/delphos_domain/`, its own uv project with no dependencies at all), published through a facade that re-exports the labels and the `resolve_*` helpers. The backend depends on it as a path dependency and the backend image copies it; the pipeline's package may depend on it too, but the vocabulary itself never depends on the ML stack.
- **Alternatives:** A submodule of `delphos_ml` (rejected, and **not** for the obvious reason: importing any submodule of a package executes that package's `__init__.py`, and `delphos_ml/__init__.py` re-exports the artifact loader, which imports scikit-learn — so `import delphos_ml.domain.labels` pulls sklearn, pandas, numpy, scipy, pyarrow and joblib into the backend's process. A submodule isolates the *file*, not the *import*); a lazy `delphos_ml/__init__.py` behind a PEP 562 module-level `__getattr__` (rejected: it fixes the import but not the install — the heavy wheels are still resolved and downloaded, because `delphos_ml`'s own project metadata declares them — and it edits a facade every existing consumer depends on); the backend keeping its own copy of the labels (rejected: two copies of a taxonomy that must agree).
- **Consequences:** The backend's install stays small, `import delphos_domain` stays light, and the vocabulary becomes a shared **contract** rather than a submodule of a package that happens to be shared. As a leaf with no dependencies it adds no version-alignment burden under [ADR-013](#adr-013-per-component-uv-projects-over-a-root-uv-workspace), and the compose build context is already the repository root, so no compose change is needed. The copy is the frontend's, verbatim: `Attack`/`Midfield`/`Defender` render as `Ataque`/`Mediocampo`/`Defensa` and the twelve sub-positions as `Delantero Centro`, `Extremo Derecho`, `Extremo Izquierdo`, `Segundo Delantero`, `Mediapunta`, `Mediocentro`, `Pivote Defensivo`, `Interior Derecho`, `Interior Izquierdo`, `Defensa Central`, `Lateral Derecho` and `Lateral Izquierdo`. A key the vocabulary does not manage resolves to a neutral Spanish placeholder (`Posición Desconocida`, `Subposición Desconocida`) rather than to the raw English, so unmanaged English can never reach the report. The role the report prints resolves from the **sub-position** first and then the position, exactly as the design preview's chain does.

### ADR-021: The report cache key includes the model and the prompt version

- **Context:** The report cache is keyed on `(player_id, model_run_id, report_type)`. But the report prose is produced by an LLM and a prompt, and neither is in the key. `model_run_id` identifies the **ML** model run, not the language model, so a change of language model or of prompt would keep serving the old prose indefinitely — and a `report_type` typo would create a second entry for a report that does not exist.
- **Decision:** The cache key is `(player_id, model_run_id, report_type, llm_model, prompt_version)`, and `app.reports` records the provenance that makes it possible: `source` (`llm` or `deterministic`), `llm_model` and `prompt_version` (migration `0004`). `prompt_version` covers the **sampling configuration** as well as the prompt text — `v2-t0.7-p0.8-k20` — because the report path is non-deterministic and a temperature change is a change in output as real as a prompt change; the version string is rebuilt from the live parameters so the cache key cannot drift from the configuration that produced the text. The `report_type` vocabulary is narrowed to the single value that has a generator (`'scouting'`), enforced by a CHECK constraint. The **model id has one source of truth**: the cache lookup and the stored provenance both read `Settings.llm_model_name` from the same request-scoped settings object, so the key can never be built from a different id than the row it is matched against ([ADR-022](#adr-022-one-model-id-derived-on-both-sides)). Two rows are reachable with one key: the report the configured model produced, and the deterministic report the last failed generation wrote. The LLM row wins when both exist; the deterministic row is served for at most **15 minutes**, so a downed LLM costs a cached answer rather than a 120-second wait per request, and a recovered LLM replaces the fallback instead of leaving the player on the template forever.
- **Alternatives:** Keying on `model_run_id` alone (rejected: the model run is the ML model, not the LLM, so it cannot detect a model or prompt change); a separate `sampling_config` column (rejected: folding the sampling parameters into the version string keeps the cache key honest at no schema cost, and a separate column would need its own key component anyway); clearing the cache on every model or prompt change (rejected: the cache is the product's latency feature, and a sweep would also delete the history the report list shows); a free-text `report_type` (rejected: it is only ever a cache key, so a typo creates a duplicate report — the vocabulary is constrained to `('scouting')` until a second generator exists); serving the deterministic row indefinitely (rejected: the template would become permanent and the model path would never be exercised again) or never serving it (rejected: every request would pay the full LLM timeout while the model is down).
- **Amendment (2026-11-17):** the "one source of truth" clause above is superseded by [ADR-033](#adr-033-the-backend-falls-back-to-a-second-inference-endpoint-over-zerotier): the lookup matches the model id against the **candidate set** of the configured endpoints (the primary's id plus the fallback's id), so the invariant is that the stored id is always one of the lookup's candidates. The prompt version is still one source of truth, and the endpoint is still not part of the key.
- **Consequences:** The schema carries the provenance, the report list can show which model wrote each report, and a model swap or a prompt edit stops serving stale prose. The migration is additive and reversible, and the constraint fails the migration loudly rather than rewriting data if a row carries a `report_type` outside the vocabulary. The TTL is a policy constant of the backend, not a schema property: it is the one number in the cache policy that trades a stale template for latency, and it is deliberately short enough that a recovered model replaces the fallback on the next request.

### ADR-023: Layered MVVM with ChangeNotifier and provider in the Flutter app

- **Context:** The Flutter app starts at the end of week 6, two weeks before delivery, with three screens to build in week 7. The team's agent skill `flutter-apply-architecture-best-practices` describes the layered approach Flutter's documentation recommends, and the app needs one place for HTTP, one for the translation from API shapes to what screens show, and screens that can be tested without a network.
- **Decision:** `lib/` has a data layer (`data/services/` with the one `ApiClient`, `data/models/` with one DTO per backend schema, `data/repositories/` that turn DTOs into domain models), `domain/models/` with immutable domain models and the `ValuationStatus` enum, and a UI layer (`ui/core/` for the theme, formatting, labels, shell and shared widgets; `ui/features/<feature>/{view_models,views}/`). ViewModels extend `ChangeNotifier` and receive repositories through their constructor. `provider` injects the `ApiClient` and the repositories from the root widget. There is no use-case layer until logic is shared across ViewModels.
- **Alternatives:** Riverpod (rejected: a new API to learn two weeks before delivery, and its code generation is a second toolchain); `get_it` as a service locator (rejected: hides dependencies that a constructor makes explicit); `freezed` or `built_value` for the models, as the skill suggests (rejected with ADR-025: no code generation).
- **Consequences:** Views stay lean and repositories are testable with a fake `http.Client`. The DTO and domain layers duplicate field lists, which is the price of keeping backend names and nullability out of the widgets.

### ADR-024: go_router with the URL as the explorer's state

- **Context:** The explorer combines filters, a page number and an open dossier, and DESIGN.md §4 has other views open the explorer at a given player. A web app also gets reloads, the back button and shared links, which in-memory state loses.
- **Decision:** `go_router` (18.1.4) with path URLs. The explorer's whole state is its query: `/explorador?estado=&posicion=&arquetipo=&q=&pagina=&jugador=<id>`, with Spanish names and values, parsed by `ExplorerQuery`; the dossier is open exactly when `jugador` is present. An unknown or malformed value is dropped instead of failing: a search longer than 100 characters, and any id that is not one to ten ASCII digits up to 2147483647 (`parseRouteId`, shared with the comparator path). The comparator is `/comparador/:playerId`, with a bare `/comparador` for the sidebar link and as the fallback for a bad id. `/arquetipos` is view 3, `/` redirects to `/explorador`, and an unknown path shows a not-found page, without the shell, with a link back to the explorer. Each module page builds the sidebar and top bar itself instead of sitting in a `ShellRoute`: a `ShellRoute` puts the page in a nested navigator whose route focus scope traps Tab, so keyboard focus never reached the sidebar. Every page sets its browser tab title ("Explorador de Mercado · DelphosFootball"), and the app title is "DelphosFootball · Dirección Deportiva". The dossier follows the URL as well: Escape, the close button, the browser's back button and activating the open player's row all remove `jugador`. A filter or page change that drops the open player from the table closes the dossier, but a link that opens a player who is not on the first page keeps it open, because the table is paged on the server and that player may simply be on a later page. There is no chat route or nav item until the chat screen exists.
- **Alternatives:** Navigator 2.0 by hand (rejected: the parsing and restoration code `go_router` already provides); keeping filters in a ViewModel only (rejected: a reload or a shared link would lose them); English URL values (rejected: the link is part of the Spanish product surface); a `ShellRoute` for the chrome (rejected after testing: the focus trap above).
- **Consequences:** Reload, back and forward, and shared links restore the same view. Every navigation goes through `context.go` with the `Routes` constants. The shell is rebuilt on each navigation, so it must stay stateless; state that has to survive a module switch belongs in a ViewModel above the router. The production server must fall back to `index.html` for paths without a file extension, which `frontend/nginx/default.conf.template` does.

### ADR-025: A hand-written Dart HTTP client against the OpenAPI contract

- **Context:** [Future work](#11-future-work) left open whether the Dart client is generated from the OpenAPI spec or hand-written. The W7 surface is seven endpoints with small schemas, and two backend changes are already planned (`fair_value_eur` and `age` in the player list).
- **Decision:** One `ApiClient` on `package:http` (1.6.0), written by hand. It decodes every body as UTF-8, maps a non-2xx answer to an `ApiException` carrying the RFC 9457 `status`, `title` and `detail`, maps a missing answer (a refused connection, a CORS rejection, a timeout) to a distinct `ApiNetworkException`, and treats a 2xx body that is not a JSON object as a `FormatException`. Every request is an `http.AbortableRequest` whose abort trigger fires at the timeout, so a timed-out request is cancelled in the browser instead of running on behind a failed future; this matters most for the 300 s report call. Each DTO parses its schema with Dart 3 map patterns plus small helpers for optional fields; a present field of the wrong type fails loudly, and an absent optional field is `null`. `main.dart` creates the one client and owns it for the page's lifetime. There is no `build_runner` and no generated code.
- **Alternatives:** An OpenAPI generator (rejected: a Java or Node toolchain or `build_runner` in the build, generated code nobody reviews, and a regeneration step on every backend change); `json_serializable` (rejected: `build_runner` for seven small schemas); `dio` (rejected: interceptors and adapters the app does not need, and a larger dependency than `http`).
- **Consequences:** The DTOs can drift from the backend schemas with nothing to catch it but the repository tests; an OpenAPI drift check stays in [Future work](#11-future-work). Tolerating absent optional fields lets the frontend ship before the backend adds them. A known gap on the backend side: an unhandled exception becomes a 500 that leaves the server without CORS headers, so the browser hides the response and the client reports it as an `ApiNetworkException` rather than an `ApiException`. Adding CORS headers to error responses is a backend follow-up.

### ADR-026: Bundled fonts and flags, no third-party requests from the client

- **Context:** The design preview loads Archivo and Source Serif 4 from Google Fonts and flags from FlagCDN, and a default Flutter web build loads CanvasKit from `www.gstatic.com` and its fallback fonts (Roboto, then Noto) from `fonts.gstatic.com`. The product claims that scouting data stays on the club's servers ([ADR-004](#adr-004-local-llamacpp-gguf-as-the-sole-llm-provider)), and every one of those requests tells a third party who is using the tool and when.
- **Decision:** The client makes no third-party request except for the dataset's own portrait and crest URLs. Everything else is served from the app's own origin:
  - CanvasKit: every build runs with `--no-web-resources-cdn`, so the engine loads from `canvaskit/` in the build.
  - App fonts: Archivo (variable, with the `wdth` axis for the condensed cut) and Source Serif 4 (variable, roman and italic) are bundled under `assets/fonts/` with their OFL licence files, which also ship as assets.
  - Engine fallback fonts: `web/flutter_bootstrap.js` sets `fontFallbackBaseUrl` to `fonts-fallback/` on the same origin, and only Roboto is bundled there (`web/fonts-fallback/roboto/v32/KFOmCnqEu92Fr1Me4GZLCzYlKw.woff2`, the path the engine requests, with its OFL). The Noto fallback set is not bundled, so a glyph that Archivo, Source Serif 4 and Roboto all lack renders as a missing glyph: the fallback request gets a 404 from our own server, and after repeated failures the engine stops asking. That is the trade-off taken: text outside Latin scripts may show empty boxes, in exchange for no font request to Google.
  - Flags: the public-domain w80 PNGs from Flagpedia, downloaded once into `assets/flags/<code>.png` for the 199 codes the country table uses, with `assets/flags/LICENSE.md` for the source and attribution. The country table covers all 202 `country_of_citizenship` values in the clean data; a country without a correct flag (Chinese Taipei) shows none.
  - Portraits and crests: a URL survives only when it is https on `img.a.transfermarkt.technology` or `tmssl.akamaized.net` (`allowedImageUrl`, applied in every DTO mapping); anything else shows the placeholder. Both hosts answer with `Access-Control-Allow-Origin: *`, so `Image.network` fetches the bytes and CanvasKit decodes them. There are no HTML `<img>` platform views: a 50-row table with a portrait and a crest per row would need a hundred of them.
  - The nginx image enforces this with a Content Security Policy: `img-src` and `connect-src` list the same two hosts (the bytes are fetched, so `connect-src` needs them too), and `font-src` and `script-src` allow only the app's origin.
- **Alternatives:** `google_fonts` (rejected: it fetches the fonts at runtime from Google); FlagCDN at runtime as in the preview (rejected: a third-party request per flag); flag emojis (rejected by DESIGN.md §6, and Windows renders them as letters); bundling the Noto set (rejected: tens of megabytes for scripts the dataset's Latin names do not use).
- **Consequences:** About 2.7 MB of app fonts, 63 KB of Roboto and 300 KB of flags in the build, no font flash from a slow network, and an app that works offline from everything but the backend and the dataset's images. The built `flutter.js` and `main.dart.js` still contain the gstatic URLs as defaults, but the build configuration overrides both. A new country needs a table row and a flag file: `countries_test.dart` checks that the set of flag files equals the set of flag codes in the table, and spot-checks Spanish names. The allowlist and the CSP's `img-src` and `connect-src` must change together. DESIGN.md §1 and §6 still describe FlagCDN for the preview; the app follows this ADR.

### ADR-027: Desktop layouts from 1280 to 1920 px with one dossier breakpoint

- **Alternatives:** A phone layout (rejected: no user reads a market table on a phone, and it would double the layout work in the last two weeks); one fixed width as in the preview (rejected: a 1280 px laptop would scroll horizontally).
- **Amendment (2026-11-11):** two market-table columns are wider than DESIGN.md §4's figures, measured with the bundled Archivo: Brecha is 128 px (not 120), so the widest verdict pill ("Sobrevalorado", 98 px with its padding) never clips, and Posición with the dossier open is 142 px (not 130), so its longest single word ("Mediocentro", 74 px beside the 36 px glyph) never breaks inside the word; a label wraps only between words. The full-page dossier below 1100 px still replaces the table, so closing it builds a fresh table. Splitting the listeners follows from the same profile: the screen listens to `ExplorerViewModel` only, and the dossier panel listens to `DossierViewModel` through its own `ListenableBuilder` (the `dossierFocus` `Focus` wraps that builder, so the focus node survives panel rebuilds), so a section answer no longer rebuilds the filter bar and the visible rows. The selected-row highlight comes from the URL query held by `ExplorerViewModel`, not from the dossier.

### ADR-028: Report HTML rendered with flutter_widget_from_html_core (superseded in the frontend)

- **Context:** `POST /reports/generate` returns three `<p>` paragraphs with `<strong>` and `<em>`, escaped by the backend for an HTML text context ([ADR-019](#adr-019-the-deterministic-renderer-is-the-fallback-and-the-quality-baseline)). The preview injects that HTML with `innerHTML`; Flutter renders to a canvas and has no `innerHTML`. The text comes from a language model and from database fields, so the client treats it as untrusted even after the backend's escaping.
- **Decision:** Render the report with `flutter_widget_from_html_core` (0.17.4), the core package without the optional extensions, styled with the Source Serif 4 prose style. Only the dependency is added today; the screen comes with the dossier, and it must follow these rules:
  - Allow only `p`, `strong`, `em` and `br`. Any other element is unwrapped to its text.
  - Never render `img` or `picture`, so a report cannot make the browser fetch a URL.
  - No links: `a` is unwrapped to its text, and no `onTapUrl` handler launches anything.
  - Strip `style`, `class` and every other attribute before rendering.
  - Never use `HtmlElementView`, `innerHTML`, `iframe` or media elements.
  - Cap the rendered content at about 20 KB and drop the rest.
  - The report widget's tests must include the input `<p onclick=x><img src=//evil><a href=javascript:1>t</a><script>y</script></p>` and assert that the only rendered text is `t`.
- **Alternatives:** An `HtmlElementView` with a real `<div>` (rejected: a platform view per report, live DOM from model output, and text that would not follow the Flutter theme); parsing the three tags by hand (rejected: a second HTML parser to maintain for a format the backend may extend); `flutter_html` (rejected: a larger package with features the report does not use).
- **Consequences:** The widget builds Flutter text from the HTML, so no backend markup becomes live DOM, and the allowlist above keeps a compromised model or row from adding images, links or styles. The package reads the theme from `package:flutter/material.dart` (see [ADR-030](#adr-030-material-widgets-come-from-the-material_ui-package)), which affects only link colours; the report has no links.
- **Amendment (2026-11-11):** The Resumen now renders reports. The allowlist is enforced before the package sees the HTML: `ui/core/html/report_html_sanitizer.dart` parses the report with `package:html` (0.15.7, already in the lockfile as this package's own parser, now pinned as a direct dependency) and writes back only `p`, `strong`, `em` and `br` with no attributes and re-escaped text. Every other element is unwrapped to its text, except scripts, styles, images, media, frames, `svg` and `math`, which are dropped with their content, so the required input renders as `t` alone. The input is cut at 20 KB before parsing. `HtmlWidget` then receives only that output, with synchronous building and a no-op `onTapUrl`. Sanitizing first, rather than hooking the package's widget factory, keeps the rules in one pure function that is unit-tested without rendering. The dossier first lists the player's newest stored report (`GET /reports?player_id=&limit=1`) and never starts a generation on open, because a generation can take two minutes of GPU time.

- **Amendment (2026-11-15):** The dossier no longer renders reports: the Resumen section is removed, and scouting reports live in the Asistente de Scouting chat. The frontend therefore has no report widget, sanitizer, report ViewModel, report repository or report DTO; the allowlist above has nothing to apply to, and both packages were removed from `pubspec.yaml`. If a screen renders HTML again, reinstate the sanitizer and its required test first. The backend's `/reports` endpoints are unchanged.

### ADR-029: The API base URL is a build-time define

- **Context:** A Flutter web build is static files, so the app cannot read a server-side environment variable at runtime. The browser calls the API from the user's machine, so the compose-internal name `http://backend:8000` does not resolve there.
- **Decision:** The backend URL is compiled in from `--dart-define=DELPHOS_API_URL=...`, defaulting to `http://localhost:8000`, the host port the compose `backend` service publishes. `.env.example` and the [§9 table](#9-cross-cutting-concerns) document the key. `frontend/Dockerfile` takes it as a build arg, and the compose `frontend` service passes `${DELPHOS_API_URL:-http://localhost:${DELPHOS_API_PORT:-8000}}` both as the build arg and as a runtime environment variable. At start-up, `frontend/nginx/15-delphos-api-origin.envsh` derives the origin from it for the CSP `connect-src`, which also lists the two dataset image hosts ([ADR-026](#adr-026-bundled-fonts-and-flags-no-third-party-requests-from-the-client)), and the container refuses to start when the value is not an `http(s)://host[:port]` URL. The dev server runs on port 3000, which the backend's default `DELPHOS_CORS_ORIGINS` already allows.
- **Alternatives:** A runtime `config.json` served beside the build (rejected: one more request and file to keep in sync for a value that changes per deployment, not per session); a relative URL behind an nginx reverse proxy (rejected for now: it removes CORS but adds a proxy configuration and changes how the dev server reaches the API).
- **Consequences:** Changing the URL means rebuilding the image; the compiled URL and the CSP come from the same variable, so they cannot disagree in the compose deployment. A deployment on another host must set `DELPHOS_API_URL` to an address the browser can reach and add the app's origin to `DELPHOS_CORS_ORIGINS`.
- **Container start-up (2026-11-12):** two defects stopped the container on a Windows checkout with `core.autocrlf=true`. First, the sourced `15-delphos-api-origin.envsh` kept its CRs and failed with `: not found`; the root `.gitattributes` now forces LF on it, on `frontend/nginx/*`, on `frontend/web/**`, on `*.sh` and on the pubspec and Dockerfiles, and the build stage of `frontend/Dockerfile` also strips CRs from `nginx/*`, so a tree checked out before the attributes existed still builds with `docker compose build`. Bind-mounting `nginx/` (the recipe in `frontend/AGENTS.md`) bypasses that strip, so such a clone must delete the nginx files and run `git checkout -- frontend/nginx/` to refresh them. Second, a Docker tmpfs mounts as `root:root`, so the entrypoint could not render the templates into `/etc/nginx/conf.d`; the compose tmpfs entries for `/tmp`, `/var/cache/nginx` and `/etc/nginx/conf.d` now carry `uid=101,gid=101`, the nginx user, plus `size` caps (16m, 16m, 1m) and `noexec,nosuid,nodev`.

### ADR-030: Material widgets come from the material_ui package

- **Context:** Flutter 3.47 moved the Material library into the `material_ui` package; the framework still ships `package:flutter/material.dart` as a separate copy. `go_router` 18 imports `material_ui` and detects the app with `findAncestorWidgetOfExactType<MaterialApp>()` using that package's type. A `MaterialApp` from the framework copy is a different type: go_router would not find it and the pages would not read the app's `Theme`.
- **Decision:** The app depends on `material_ui` (1.11.0) directly and imports `package:material_ui/material_ui.dart` everywhere it needs Material, including its localization delegates for the es-ES locale; widget-only files import `package:flutter/widgets.dart`. `uses-material-design` is `false`, because the design uses no Material icons.
- **Alternatives:** The framework's `package:flutter/material.dart` (rejected: the type split above); an older `go_router` built on the framework copy (rejected: it pins the router to a superseded Material and loses fixes).
- **Consequences:** A dependency that still imports the framework copy (as `flutter_widget_from_html_core` 0.17.4 did before ADR-028's amendment removed it) sees no app theme and uses its defaults; `material_ui` provides `MaterialUiCompatibilityBridge` if a screen needs that theme bridged. `Icons.*` renders nothing; the few glyphs the design needs are drawn in code.

### ADR-031: The inference server is published on a named host address

- **Context:** The `inference-chat` service had no published port at all, so the OpenAI-compatible API was reachable only from inside the compose network. [docs/LLM_FALLBACK_PLAN.md](LLM_FALLBACK_PLAN.md) needs a second inference endpoint on another machine, reached over ZeroTier: its §4 "The remote end" requires the serving host to publish the port, and its §4 Option A requires the *client* to reach the peer's ZeroTier IP. The llama.cpp server API is unauthenticated, and every prompt it serves carries player data.
- **Decision:** The service publishes its container port `8080` on a host address named by `DELPHOS_INFERENCE_PUBLISH_IP` (default `127.0.0.1`) at the host port `DELPHOS_INFERENCE_PUBLISH_PORT` (default `8081`). The default keeps the server local-only; setting the address to the host's ZeroTier address exposes it to exactly that network. The container still listens on `0.0.0.0` internally so the compose network can reach it.
- **Alternatives:** Publishing on `0.0.0.0` (rejected: it exposes an unauthenticated inference API to the LAN and to every Docker bridge on the host); `network_mode: host` (rejected: it costs port isolation and compose DNS, so every service URL would have to change); a llama.cpp API key on the exposed server (deferred for now, and it is the right next step — see Consequences); a reverse proxy in front of the server (rejected for now: it adds a component to a two-machine setup for no gain).
- **Consequences:**
  - The change adds a host listener that did not exist before, on `127.0.0.1:8081` by default. That host port must be free; a deployment that already uses 8081 must set `DELPHOS_INFERENCE_PUBLISH_PORT`.
  - The published address must name an interface that is **up and holding that address** when the container starts; otherwise the bind fails with `cannot assign requested address` and the inference path is down. A ZeroTier address is per host and per network membership, so it belongs in the gitignored `.env` and must be updated when it changes.
  - `0.0.0.0` must not be used. Nothing enforces this: it is a policy in this ADR and in `.env.example`, and the compose file will happily publish it if the variable says so.
  - The API is unauthenticated. Measured on the shipped image build (`b9294`), the published surface is `POST /v1/chat/completions`, `POST /completion`, `POST /apply-template`, `POST /tokenize`, `POST /detokenize`, `GET /props`, `GET /slots`, `GET /lora-adapters`, `POST /lora-adapters`, `GET /models`, `GET /v1/models` and `GET /health`. `POST /props`, `POST /slots/{id}`, `/v1/embeddings` and `/rerank` answer 501 on this build. `/slots` returns slot state and token counts, not prompt text, and the model directory is mounted read-only. `POST /lora-adapters` accepts an arbitrary server-side path and answers `{"success": true}`, but on this build it registers no adapter and the generation is unchanged; a build that did register one would change every subsequent completion, including the reports the club reads.
  - The published container is bounded: a read-only root, no capabilities, `no-new-privileges`, a 64 MiB writable `/tmp`, `mem_limit: 12g`, `pids_limit: 256` and `restart: unless-stopped`, so a peer cannot exhaust the host's RAM and a crashed server comes back on its own.
  - A published peer therefore bypasses the backend's question cap, token caps, concurrency semaphore and read-only tool allowlist, and can occupy the four server slots. The next step is an API key: `llm_api_key` in `backend/src/delphos_backend/core/config.py`, an `Authorization: Bearer` header in `services/llm_client.py`, `LLAMA_ARG_API_KEY` on the server and `DELPHOS_LLM_API_KEY` forwarded to the backend (the backend service forwards the two primary LLM keys and the four fallback keys today), plus the healthcheck, which must keep working when the server requires the key. A ZeroTier ACL that pins `tcp/8081` to the peer's address is the cheaper first step, and the two are complementary: the ACL is the compensating control for the unauthenticated API, and it must be in place before a peer is let into the network.
  - The named-address argument holds only while the rest of the stack is not published wider. On the analyst host the `backend` service is published on `0.0.0.0:8001` with **no authentication at all**, and the `db` service on `0.0.0.0:5433` with the default credentials, so a LAN or ZeroTier peer reaches every published row and `/chat` directly — a strictly wider path to the same data than the inference port. Binding both to `127.0.0.1` is a separate change and is not part of this ADR, but it is what makes the inference exposure marginal rather than the dominant one.
  - The image tag is mutable by design, because the same variable selects the CPU variant. The digest verified on the analyst host is recorded in [§4.6](#46-llm-inference-service); re-verify it after every `docker compose pull` and record a new one.

### ADR-032: The inference container is given the GPU explicitly, with a CPU override file

- **Context:** The CUDA build of llama.cpp does not fail when it cannot see a GPU: it logs `no usable GPU found, --gpu-layers option will be ignored` and serves on the CPU, which is roughly an order of magnitude slower than the 40-60 t/s the report path assumes. A silent CPU fallback is a performance bug that looks like a working service. The opposite failure exists too: a GPU *request* on a host with no NVIDIA card is a container-creation error, so the request cannot simply be added and forgotten.
- **Decision:** The base compose file declares `gpus: all` on the `inference-chat` service, and `docker-compose.cpu.yml` resets that key with `gpus: !reset null` for a host without a card. The CPU variant is run as `docker compose -f docker-compose.yml -f docker-compose.cpu.yml up -d inference-chat`, with `LLAMA_ARG_IMAGE=server` and a CPU-sized model.
- **Alternatives:** Leaving the CPU fallback implicit (rejected: silent CPU serving, the failure mode above); a runtime gate in the compose file (rejected: compose cannot express a conditional key); a second complete compose file (rejected: it would drift from the base one on every change); pinning the GPU request to the CUDA build only and dropping the CPU variant (rejected: the CPU variant is the documented fallback for a host without a GPU).
- **Consequences:** The base file needs Docker Compose 2.30 or newer, Docker Engine 25 or newer and the NVIDIA Container Toolkit (bundled in Docker Desktop); the `!reset` override itself needs 2.24, so the pair needs 2.30. The override file uses a YAML tag that a plain YAML parser does not know, so any tooling that parses the compose files as YAML must register `!reset` rather than fail on it. The start-up check for the GPU is the startup log line `CUDA0`, not the container's health.

### ADR-033: The backend falls back to a second inference endpoint over ZeroTier

- **Context:** The backend owns exactly one inference call site (`backend/src/delphos_backend/services/llm_client.py`), and it talks to one llama.cpp server. When that server is down — the container is stopped, the host has no GPU, the model is not loaded — the report path degrades to the deterministic renderer (a 200 with `source="deterministic"`) and `/chat` answers 503. [ADR-031](#adr-031-the-inference-server-is-published-on-a-named-host-address) publishes that server on the host's ZeroTier address, so a peer machine on that network can serve the same OpenAI-compatible API. [docs/LLM_FALLBACK_PLAN.md](LLM_FALLBACK_PLAN.md) is the working plan for the application half of this: a second endpoint, used automatically when the first is unusable, without changing the report or chat contracts.
- **Decision:** The backend calls a **second, remote endpoint** when the primary one cannot serve the call. The endpoint is decided **before the answer of that call exists**, and it is **pinned for the whole turn**: one turn is served by one endpoint, never by two. Five settings drive it (`DELPHOS_LLM_FALLBACK_API_URL`, `DELPHOS_LLM_FALLBACK_MODEL_NAME`, `DELPHOS_LLM_FALLBACK_TIMEOUT_SECONDS`, `DELPHOS_LLM_FALLBACK_PEER_CIDR`, `DELPHOS_LLM_PRIMARY_PROBE_SECONDS`); an empty fallback URL disables the feature completely, and the behaviour without it is byte-for-byte the behaviour before this decision. The mechanism is:
  1. **A reachability probe.** `GET {base_url}/models` with a short timeout (`llm_primary_probe_seconds`, 5 s by default), against **both** endpoints. The probe carries no prompt and no credential, so an endpoint that cannot answer it never receives either. An endpoint counts as **serving** only when it answers HTTP 200 with a JSON body that carries a model list (the shipped llama.cpp answers its OpenAI-compatible route with `{"object": "list", "data": [...]}`; a body reporting a `models` list is accepted as well). A transport error, a non-200, an undecodable body and a body without a model list all mean "not serving". The verdict is cached for about five seconds, so a burst of requests does not re-probe, and concurrent probes of one URL share a single request.
  2. **An endpoint that is not serving is skipped.** The call goes straight to the fallback; a refused connection costs the probe timeout, not the primary's 120 s. **The fallback is used only when its own probe says it is serving**: a dead or wrong address never receives a prompt, and the peer's reachability is known before anything leaves the host.
  3. **A failing primary call is retried** on the fallback, with the fallback's own budget (`llm_fallback_timeout_seconds`, 60 s by default), after the fallback has been probed. If the fallback fails too, one `InferenceError` is raised, naming both failures and chaining the primary's; when both failures were timeouts, the raised error is an `InferenceTimeout`, so the report path spends no repair attempt on it.
  4. **The request body names the serving endpoint's model id**: the primary's, or the fallback's (`llm_fallback_model_name`, or the primary's when that is empty). `CompletionResult` carries the endpoint that served the call and the model id asked for, and the report path stores that plain model id in `app.reports.llm_model`. **No database schema change is involved.**
  5. **The report cache accepts either configured model.** The lookup matches `llm_model = ANY(...)` against the candidate set — the primary's id plus the fallback's id when it is set — so a report written by one endpoint answers the next request even when the other endpoint produced it. The invariant is therefore that **the stored model id is always one of the lookup's candidates**, not that the lookup and the provenance read the same setting ([ADR-021](#adr-021-the-report-cache-key-includes-the-model-and-the-prompt-version) still keys on the model and the prompt version). The endpoint is **not** part of the cache key: the column names the model that wrote the text, not the machine that served it. With the shipped configuration — the same model id on both endpoints — a report produced by either endpoint may be served from cache to the other, because the two endpoints are interchangeable producers of the same model.
  6. **The fallback URL is guarded by an allowlist, not by a syntax check.** `DELPHOS_LLM_FALLBACK_API_URL` must be empty or an `http`/`https` URL whose host is an **IP literal inside `DELPHOS_LLM_FALLBACK_PEER_CIDR`** (default `10.0.0.0/8`, the RFC1918 `10/8` block — the range ZeroTier managed networks usually sit in; an operator must narrow it to the peer's actual subnet). A hostname is refused: it could resolve anywhere, and DNS would defeat the allowlist. Loopback, link-local, unspecified, multicast and reserved addresses are refused whatever the range says. No userinfo, no query string, no fragment and no whitespace — an operator may put an API key in the query, and it must not reach the logs. An invalid value fails the settings load with a message naming the variable (`DELPHOS_LLM_FALLBACK_API_URL`, or `DELPHOS_LLM_FALLBACK_PEER_CIDR` when the range itself is wrong); the range must not be empty while a fallback URL is set, because without it there is no allowlist, and it must sit **inside a private range** (`10/8`, `172.16/12`, `192.168/16`) — a range that admits the public internet would void the allowlist it exists to provide.
  7. **The fallback's served model id must match.** The expected id is `llm_fallback_model_name`, or the primary's id when that one is empty, and the comparison is **strict** in both cases: a peer that reports another model is **refused** (logged at WARNING), never warned about, so its prose can never be stored as the club's model output. The same rule guards the answer itself: the report path compares the model id the server reported in the completion with the one that was requested, and a mismatch produces the deterministic rendering instead of a stored report.
  8. **One report's prose comes wholly from one endpoint.** The report path resolves the endpoint once, before the first answer exists, and the draft and its repair go to that endpoint: when a completion comes back, the next call of the chain is pinned to the endpoint that served it. A draft served by the fallback therefore has its repair served by the fallback too, and the stored `llm_model` — the id of the last completion — describes the whole text. The availability property is preserved: if the pinned endpoint fails outright, before any prose exists, the internal fallback may serve the **whole chain** on the other endpoint, and the repair is then pinned to that one. The price is explicit: a repair that fails on the endpoint that wrote the draft costs the report (the deterministic renderer answers instead) rather than composing one report out of two models.
  9. **A fallback naming this host's own published address is allowed, but warned about.** The team wants a backend on this box to be able to consume this box's server, so `DELPHOS_INFERENCE_PUBLISH_IP` is not refused; the backend logs a WARNING naming `scheme://host:port` that such a fallback is a second path to the same process and provides no availability guarantee. The rule that the fallback host should be a **different machine** stands next to it.
- **Alternatives:**
  - **A short timeout on the primary CALL (20 s), as proposed in [docs/LLM_FALLBACK_PLAN.md](LLM_FALLBACK_PLAN.md) §6 decision 1 — rejected, and this is the deliberate deviation from that plan.** A healthy report generation legitimately takes 30-60 s (a 1,400-token Spanish report at 40-60 t/s plus prefill), so a 20 s call timeout would abandon healthy generations and turn a working primary into a fallback that the cache then treats as a different model. The plan's own reasoning — "one request can run four minutes" — is answered by the probe instead: a **dead** primary is detected in seconds, and a **refused connection** fails instantly, while a healthy primary keeps its full 120 s budget.
  - **An overall deadline for the two attempts** (rejected: it couples the two budgets and makes the fallback's share depend on how long the primary happened to take, which is the opposite of what a slower remote link needs).
  - **A mid-stream switch** for the streamed chat response (rejected: impossible once the 200 headers are sent; the endpoint is decided before the first byte, and the inference call itself is not streamed).
  - **Buffering the first token of a stream and falling back if none arrives** (rejected: it adds latency to every turn and complicates the failure semantics).
  - **No fallback for the streamed chat path at all** (rejected: the probe decides the endpoint before the response starts, so the streamed path gets the fallback for free).
  - **An API key on the fallback endpoint** (rejected for now, and deliberately: the compensating control for the unauthenticated llama.cpp API is a **ZeroTier ACL pinning the published port to the peer**, a controller-side rule that needs no code and also covers the native routes. An API key is the right follow-up, together with `llm_api_key` in the settings and an `Authorization` header — see ADR-031).
  - **A third value for `app.reports.source`** ("llm-fallback") (rejected: the schema must not change. The earlier justification — "the endpoint is already recorded in the provenance through the model id" — was wrong: with one shared model id the two endpoints are interchangeable producers of the same model, so the id does **not** identify the endpoint. The endpoint is in the **logs** only, and the report list cannot tell a peer-served report from a locally served one.)
  - **The endpoint in the cache key** (rejected: it would need a schema change and it would make a fallback-produced report unreachable for the next request, so every `POST /reports/generate` would regenerate it — 30-60 s of remote inference — and insert another `app.reports` row, bypassing the fifteen-minute window that protects the deterministic row).
- **Consequences:**
  - **The worst case is now the primary's timeout plus the fallback's timeout** — 120 s + 60 s by default — for one request. A report generation that finds a dead-but-listening primary waits the longest. The probe removes the common case (a stopped container refuses the connection and is skipped in seconds), and the deterministic renderer still answers 200 when both endpoints are gone.
  - The probe is one extra `GET` against an endpoint on the request path, and its verdict is reused for five seconds, so a burst of requests does not re-probe. The **fallback is probed too**, before it is given anything: the probe is the control that stops a wrong or dead address from receiving a prompt. A **failed** attempt drops the verdict of that endpoint, because a failure contradicts "serving" — so the next request re-probes it and a recovered primary is picked up at once. A **successful** attempt keeps it: the endpoint has just answered, and re-probing it would cost a request per call for nothing. An endpoint the probe never reached (because it judged the endpoint not serving) keeps its verdict for the rest of the TTL, which is what makes a dead primary cost one probe per five seconds rather than one per request.
  - **The allowlist has an honest limit.** A **transposed address inside the allowed range still passes the check**: the range says where the peer may sit, not which machine it is. What stops that case is the probe (a wrong address inside the range is unlikely to answer it — but a host that runs an OpenAI-compatible server would) and the ZeroTier ACL that pins the published port to the peer. The rule is a guard against the plausible mistakes — a public host, an address of another network — not a proof of identity.
  - **A turn is pinned to one endpoint.** The chat tool loop resolves the endpoint once, before the first answer of the turn exists, and every call of that turn goes to it: a turn is never composed of two models' output, and the **database tool results of the chat loop cross the ZeroTier link** when the fallback serves the turn — the same link the report's fact card crosses. A turn whose pinned endpoint dies mid-turn fails as a whole; the peer is not switched to in the middle of a turn, because the tool results have already been sent to the first one.
  - **The fallback host should be a different machine.** Pointing `DELPHOS_LLM_FALLBACK_API_URL` at this host's own published inference address is a second path to the same process: when the container is down, the fallback is down too, and the feature buys no availability. The backend allows it — the team wants a backend on this box to be able to consume this box's server — and warns about it at start-up and whenever the fallback is checked.
  - The fallback is **unauthenticated**: every prompt crosses the ZeroTier link, so the ACL must be in place before a peer is let into the network (ADR-031). The backend is published on `0.0.0.0` without authentication, so a dead primary lets any caller push prompt traffic at the peer; that is a consequence of the missing authentication recorded as a follow-up in ADR-031, and no circuit breaker is built for it here.
  - The chat path holds its concurrency semaphore across both attempts, so one logical call holds one slot ([docs/LLM_FALLBACK_PLAN.md](LLM_FALLBACK_PLAN.md) §5.3).
  - The report contract does not change: a report is a 200 with a body, degraded or not, and the chat failure semantics do not change either (a problem response before the first byte, an `error` event after it).
  - **The logs say which endpoint served a call.** The endpoints are named as `scheme://host:port` — never the full URL with credentials, and never a prompt. Three WARNING lines cover the peer path: the decision ("the primary … is unreachable (…); the fallback … serves the turn", once per turn), the call the fallback served ("the fallback inference endpoint … served the call", once per call), and the report ("the scouting report was served by the fallback inference endpoint", once per report), so a peer-served report is distinguishable in the logs. While the primary stays down, the first line repeats once per turn. A failed call logs the endpoint's label and the **exception's class name**, never the exception's text: `httpx.HTTPStatusError` renders the full request URL, path and query, and an operator may put an API key in that query.
  - The backend's LLM modules were split to keep every module within the 130-line rule: `llm_protocol` (the errors, the result types and the response parsing), `llm_probe` and `llm_probe_cache` (the reachability probe and its verdict cache), `llm_endpoint` (the call that reaches one endpoint) and `llm_request` (the endpoint, the options and the body of one request), `llm_targets` (the two configured endpoints), `llm_readiness` (whether one endpoint may serve: the probe's verdict, the fallback's model-id rule and the own-address warning), `llm_choice` (which endpoint serves a call), `llm_attempts` (one attempt and the error two failed attempts compose), `llm_chain` (one report's chain of completions, served by one endpoint) and `llm_client` (the public client and the public surface). The allowlist rules live in `core/peer_policy.py`, beside the settings they guard.
